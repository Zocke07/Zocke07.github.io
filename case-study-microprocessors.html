From a Truth Table to a Pipelined CPU

Two semesters, pointed in opposite directions. The first built upward in VHDL, starting from seven Boolean equations read off a truth table by hand and ending with a four-stage pipelined CPU on an FPGA. The second worked downward on an NVIDIA Jetson TX2, from a cross-compiled binary to a loadable kernel module, until user space switched hardware by writing to /dev. Neither semester produced a product. Both are why I know what the software I test is standing on.

What this page is: not a claim on the work. All of it was done in a team, two of us in the first semester and three in the second, and rather than try to sort out who typed which line two years afterwards, this is a reading of what the code does, why it works, and where it does not. The exercises belong to the course. The understanding is the part I am putting my name to.

  • 9 VHDL exercises, gates to CPU
  • 1,290 lines of VHDL in 37 files
  • 218 lines for the pipelined CPU itself
  • 4 stages, written in reverse order
  • 236 lines of kernel C, one character device
  • 5 languages in the final project
Scope and credit: none of this was solo work. The first semester's nine VHDL exercises were done in a pair; everything in the second semester, the labs as well as the final project, was done by a group of three and submitted under the group's name. Nothing below is offered as my own work. I re-read both repositories to write this rather than working from memory, so every claim points at a file I can open, including the unflattering ones. Both halves are public: Microprocessor-Based-Systems for the VHDL and Microprocessor-Based-Systems-Lab for the embedded semester, along with the demo video, of which the photograph below is a frame. Every diagram here is drawn from the source. None of the course's own slides appear on this page.

Two Semesters, Two Directions

Microprocessor Systems, autumn 2023, was VHDL on an FPGA board: eight switches for data, eight for an instruction, a row of LEDs, and six seven-segment displays. Embedded Microprocessor Systems Lab, spring 2024, was an NVIDIA Jetson TX2 running Ubuntu 18.04 on a 4.9 Tegra kernel, with a breadboard, five LEDs, a photoresistor and an MCP3008 analog-to-digital converter beside it.

The first course accumulates. Each week's exercise is built out of the previous week's file, and the last one is a processor. The second course descends. It begins in application code and ends inside the kernel.

  1. Seven-segment decoderSeven Boolean equations, one per segment, taken off a truth table by hand. The second objective needed three digits, so the same seven equations are pasted three times with every signal name suffixed, twenty-one outputs in one file, no components anywhere.
  2. Adder and subtractorEight one-bit full adders chained by their carries into an eight-bit adder, then the same again with a full subtractor. This is where the decoder stopped being copied and became a component in a package, instantiated by name.
  3. BCD adderBinary addition gives the wrong answer in decimal, so each digit tests for a carry or a result above nine and adds six to correct it. Sixteen full adders and one boolean expression per digit, structural the whole way down.
  4. Simple ALUA one-bit slice built from two multiplexers, a full adder and a four-way output select, then seven of them generated in a loop and wired carry to carry.
  5. Universal shift registerEight bits, clear, parallel load, and a direction select, written as two loops that move every bit one position and feed the serial input into the vacated end.
  6. State machineThe two-process form: one combinational process deciding the next state, one clocked process committing it. Six states, one input. This is the piece everything after it is made of.
  7. Restoring dividerDivision as a state machine over eight iterations: subtract the shifted divisor, and if the result went negative, add it back and shift a zero into the quotient instead of a one. Six states, and a comment in the loop counter that still reads --7 or 8?.
  8. Simple CPUThe divider's state machine promoted to an instruction cycle: fetch, read Rs, read Rt, operate, write back, driven by a step counter. Eight opcodes, four registers, one at a time.
  9. Pipelined CPUThe same instruction set, except all four stages run at once and an instruction that needs a value still in flight gets it forwarded rather than waiting. 218 lines.

One detail survived the whole way. The seven equations from the first week are still in the final project, and not in spirit: character for character, they are the same expressions with the input signals renamed. 

-- lab1_1.vhd, the first exercise of the course: segment a, off the truth table
a  <= (X and not Y and not Z) or (W and X and not Y)
   or (not W and not X and not Y and Z) or (W and not X and Y and Z);

-- final/hex.vhd, the last one: the same equation, renamed
a1 <= (s2 and not s1 and not s0) or (s3 and s2 and not s1)
   or (not s3 and not s2 and not s1 and s0) or (s3 and not s2 and s1 and s0);

All seven segments match under the renaming W,X,Y,Z to s3,s2,s1,s0. The processor's display path is the first exercise of the course, untouched.

The tidy version of this story is that each semester got closer to the metal. The version worth more is narrower and less flattering: both semesters end with an indicator that is trusted further than it has earned. On the FPGA it is a hazard LED that cannot light for the case the assignment sheet uses as its example. On the Jetson it was a browser panel that reports what it asked for and never once reads back what happened.

The Pipeline Is a Statement Order

A pipelined processor is four stages running in the same clock cycle on four different instructions, with a register between each pair holding what the previous stage produced. In VHDL you would expect that to be four signals and four processes. It is one process and four variables, and the reason it works is an ordering trick that is easy to read past, which is what I did until I sat down with the file properly.

Signals in VHDL are scheduled: an assignment takes effect after the process finishes. Variables are immediate: an assignment is visible to the next line. So if the four stages are written in reverse, write-back first and fetch last, each stage copies its predecessor's instruction forward while that predecessor still holds last cycle's value, a moment before the next statement overwrites it. The pipeline registers are not declared hardware at all. They are the gaps between four statements in a particular order. 

-- PipelineCPU.vhd, condensed: the four stages as they appear in the file
process(Clock)
  variable tmpIns1, tmpIns2, tmpIns3, tmpIns4 : std_logic_vector(7 downto 0) := "11110000";
begin
  if rising_edge(Clock) then
    --Write back
    tmpIns4 := tmpIns3;        -- reads what EX held last cycle
    ...
    --Excution
    tmpIns3 := tmpIns2;        -- only now is tmpIns3 replaced
    ...
    --Instruction decode
    tmpIns2 := tmpIns1;
    ...
    --Instruction fetch
    tmpIns1 := Instruction;
  end if;
end process;

Swap any two of those four blocks and the processor stops being pipelined. Nothing in the file says so.

The board reports the pipeline honestly, at least. A four-bit output called ExcuteStatus drives four green LEDs, one per stage, each set by the stage that owns it and cleared when that stage is holding a bubble. Feed instructions in one at a time on the clock button and you watch a single lit LED walk across the row; feed four in a row and the whole row lights. It is a four-bit trace of pipeline occupancy, and it was the only debugger the exercise had.

The Forwarding Path That Was Already There

Two instructions in a row that touch the same register are the reason pipelines are hard. add r1, r2 writes its result at write-back, two stages after the next instruction has already read its operands. The assignment allotted ten percent for detecting that collision and stalling, and another ten for forwarding the value instead. So there is a detector. 

-- PipelineCPU.vhd, in the decode stage, verbatim
if ((not(tmpIns3(3 downto 2) = "00")) and
    ((tmpIns3(3 downto 2) = tmpIns2(3 downto 2)) or
     (tmpIns3(3 downto 2) = tmpIns2(1 downto 0)))) then
  HazardDetection <= '1';
  tmpRs := excuteResult;
else
  HazardDetection <= '0';
  case tmpIns2(3 downto 2) is
    when "00" => tmpRs := r0tmp;
    ...

tmpIns3 is the instruction in execution, tmpIns2 the one being decoded. Bits 3 and 2 are the destination register, bits 1 and 0 the second operand.

It demonstrated. The red hazard LED lights on the obvious collisions, the arithmetic comes out right, and on a lab bench that is the end of it. Reading it now, two things are true that a demo cannot show, and they point in opposite directions.

The forwarding had already happened, one statement earlier

There are two register files in this design and only one of them looks deliberate. The signals r0 to r3 are written at write-back and read by nothing except the seven-segment displays. The variables r0tmp to r3tmp are written in execution and are what the decode stage actually reads. Because execution is written above decode in the same process, the shadow file already holds the result of the instruction ahead by the time the next instruction looks for its operands. The datapath forwards whether or not the detector fires, for the same reason the pipeline advances at all: statement order.

Which makes the if branch and the else branch two ways of fetching the same number. excuteResult and the shadow register the execution stage just wrote it into are equal by construction. The detection is real, but the forwarding it claims credit for is a property of the file's layout.

And where the detector does change the answer, it is wrong

The condition fires when the executing instruction's destination matches the decoded instruction's first or second operand field, and then assigns into tmpRs, the first operand, either way. When the collision is on the second operand only, that overwrites a register the instruction was not asking about. add r1, r2 followed by add r2, r1 computes the new r1 plus itself and stores that in r2. The else branch, the one the detector exists to improve on, would have got it right.

The leading term is a second mistake wearing the same coat. not(tmpIns3(3 downto 2) = "00") excludes R0 as a destination, because a bubble is encoded as 11110000 and its destination field reads as R0. The intent was "ignore bubbles" and the test was written against the wrong four bits: the opcode says what an instruction is, the destination field never did. The cost is that the hazard LED stays dark for every collision on R0, including add r0, r1 followed by sub r0, r2, which is the worked example printed on the assignment sheet. The arithmetic is still correct, because the shadow register file does not care what the detector thinks. An indicator that cannot report the documented failure is not an indicator.

This is the part I would rather have understood in 2023. The demo passed because the check was that the lamp lit, not that it lit for the right reason, and there is a straight line from that to the part of my job that is now about telling a green build from a build that merely looks green.

Down the Other Side

The second semester started above everything the first one had built and worked down through it. Its first lesson was that the compiler is not the machine: a C++ program of abstract shapes and a comparison sort, built with aarch64-linux-gnu-g++ on one computer and run on another. Nothing about the program is embedded. Everything about getting it to run is.

  1. Cross-compilePolymorphic shapes and a sort, compiled for aarch64 on a laptop and executed on the board. A makefile with CROSS_COMPILE = aarch64-linux-gnu- at the top of it.
  2. GPIO from user spaceTurning on an LED is open("/sys/class/gpio/export"), write the pin number, write "out" to its direction file, write "1" to its value file. Four file writes and no library.
  3. A GUI over the same four writesQt on the board itself: checkboxes, a slider bound to a blink period, keyboard shortcuts, and a QTimer alternating two groups of LEDs.
  4. A browser over the same four writesAn Express server serving a static page and shelling out to the lab 2 binary. The control surface moved off the board and onto anything with a browser on the same network.
  5. An analog sensor, bit by bitA photoresistor cannot be read by a digital pin, so an MCP3008 converts it and the Jetson clocks the conversation out by hand: five bits of command shifted out, twelve clock pulses shifted back in, chip select raised and lowered around the whole exchange. SPI implemented by toggling four wires in a Python loop.
  6. The browser reads backLabs 4 and 5 joined: the Express server also shells out to the Python that drives the MCP3008, and the page polls it with $.ajax on a timer instead of asking once. A threshold on the returned value switches LEDs with nobody clicking anything. This is the final project in miniature, one room instead of four.
  7. Into the kernelA loadable module that registers a character device, so the LEDs are switched by writing bytes to /dev/demo instead of by writing to sysfs.

The final project was the seven of them stacked: a room-booking panel called Smart Room Management, where four LEDs are four rooms, a fifth is a booking timer, and a photoresistor in the hall decides whether the hall light is needed. Choose rooms in a browser, set a timer, and the chosen rooms blink for its duration.

The Driver That Drove Nothing

The kernel module was worth twenty percent of the project and it is the piece that looks most like systems programming. It is 236 lines of C that register a character device on major number 60 and implement open, read, write, ioctl and release. Loading it and writing four bytes to /dev/demo switches an LED. All of that is true.

It is also not a driver. Here is the entire protocol and the entire mechanism: 

/* demo.c: the write handler's protocol is four characters wide */
copy_from_user(userChar, buf, count);
userChar[count - 1] = '\0';
strncpy(gpio, userChar, 3);   /* "255" */
value[0] = userChar[3];       /* '1', '0', or anything else meaning "read it back" */

/* and this is what the write ends up doing, from inside the kernel */
snprintf(buf, sizeof(buf), "/sys/class/gpio/gpio%s/value", gpio);
fd = filp_open(buf, O_WRONLY, 0);
vfs_write(fd, value, strlen(value), &pos);

Wrapped in set_fs(get_ds()), which is what you have to do to make the kernel accept a kernel-space buffer where it expects a user-space one. Needing that call is the smell.

The module does not touch a GPIO register. It does not call gpio_request or any part of the kernel's GPIO interface. It opens /sys/class/gpio/gpio255/value and writes a character to it, which is exactly what lab 2 did four weeks earlier from user space in about ten lines. A driver exists to be the bottom of the stack. This one climbed back up to the layer it was supposed to replace and asked that layer to do the work. It added a hop instead of removing one.

What the exercise genuinely teaches is worth separating from what it claims. It shows how a character device gets registered, why copy_from_user exists, what a major number is for, and how a module's build is tied to the exact kernel it will load into: this one is compiled against headers for 4.9.299-tegra and would not build against anything recent, because set_fs and vfs_write are gone from modern kernels for the reasons the code above demonstrates. What it does not teach is how to drive hardware, and I would have told you otherwise at the time.

What the Rubric Built

The brief awarded twenty percent for a driver, twenty for multithreading, fifteen for a web interface, fifteen for a sensor and five for notifying the user by email. Read the final project's architecture and you can recover that list from it exactly, which is the most honest thing to be said about the design. Nothing in a room-booking panel needs threads. The rubric needed threads, so the timer is threaded.

The lock is the schedule

The blinking is a pthread program: n threads, each iterating twice, each taking a mutex, toggling the four room LEDs, sleeping for one second, and releasing. The lock is held across the sleep. Taking a lock and then sleeping inside it means no two threads are ever inside the loop at once, so the threads run strictly one after another and the program's behavior is identical to a sequential loop. The mutex is not protecting shared state from a race. It is being used as the thing that makes the LEDs blink in order. It was worth twenty percent and it demonstrated cleanly, and it is a sequential program with threads drawn on it.

One number, three names

The browser labels the timer field Hour(s). The server formats the same value into an email as days. Then it divides by ten, subtracts one, and passes the result to the pthread program, which uses it as the number of threads to create, one character at a time, so a two-digit value would silently lose its second digit. Nobody noticed, because at every layer the number looked plausible for what that layer thought it was.

The wiring drifted and the fix went in at the top

Four LEDs had four GPIO numbers, and those numbers are written out longhand in every file that needs them. Lab 2 ordered them 255, 481, 392, 254. The Qt application ordered them 392, 255, 481, 254. The final project ordered them 255, 392, 481, 254. Same four wires, three different opinions about which is LED2. 

// lab04.js: the browser's LED1 is the board's LED3, resolved by renaming
let response = {
    "LED1": req.query.LED3,
    "LED2": req.query.LED1,
    "LED3": req.query.LED2,
    "LED4": req.query.LED4,
}

A permutation table, in the web server, standing in for a corrected pin map two layers down.

It is not hard to see how that happens. The checkboxes light the wrong lamps during a rehearsal, the server is the file already open, and swapping three keys in an object takes ten seconds where tracing the wiring takes twenty minutes. It worked. It also means the wiring disagreement is still in there, now with a compensating error on top, and the next person to change either one gets both.

The panel reports its own intentions

Nothing in the browser ever asks the board what state a pin is in. Checkboxes and images are set by the same click that sends the request; the Qt version goes further and reads those checkboxes back as if they were the device's state, so the interface is both the command and the record of it. The one path that does read a pin, the state branch in the user-space program, prints the answer to standard output, where the server collects it into a console.log nobody was reading. Three of the four request handlers never send a response at all, so a browser that asked for something waits for a reply that is not coming, and the page shows success because it never looked.

An interface that was never meant to be automated

The camera on the TX2 is driven by nvgstcapture-1.0, an interactive tool where you press j to capture and q to quit. There is no flag for "take one photograph and exit", so the server spawns it and types into it. 

// final.js: automating a program that only accepts keystrokes
const captureProcess = spawn('nvgstcapture-1.0', ['--prev-res=3']);
setTimeout(() => {
    captureProcess.stdin.write('j\n');                            // capture
    setTimeout(() => captureProcess.stdin.write('q\n'), 1000);    // quit
}, 1000);

Two setTimeout calls standing in for any knowledge of whether the process was ready. It is a race, and the fix is to wait for output rather than for a second.

Nobody called that testing at the time, and I would not have either. It is the same instinct: an interface built for a person, a task that has to happen the same way every time, and a program driving the controls in place of a hand. The timing bug in it is a flaky test, sitting in a course project two years before I had a word for one.

What Does Not Hold Up

The hazard detector and the driver are above, because they are the point rather than footnotes. These are the rest, turned up by reading the repositories to write this page. None of them were found at the time, by me or by anyone else at the bench.

The seven-bit ALU is missing a bit

The seven one-bit slices are produced by a generate loop with three cases: bit zero, bits strictly between one and six, and bit six. The middle condition reads (6 > i) and (i > 1), which covers bits two to five. Bit one gets no instance at all, so its result and its carry are driven by nothing and the carry chain through the rest of the word is broken. It reported correct answers on whatever was typed into the switches during the demo, and nothing on the board would have said otherwise: the number on the display looked like a number.

The set-on-less-than output was never connected to anything

The same lab's one-bit slice declares an output called set, and the seven-bit version wires the top slice's set into the bottom slice's less input, which is the textbook way to build a comparison out of a subtraction. Neither architecture ever assigns set. The wire is there in both files and there is nothing on it.

The kernel module trusts whatever user space hands it

drv_write copies count bytes into a fixed 100-byte static buffer without comparing the two numbers, then writes a terminator at userChar[count - 1] without checking that count is greater than zero. Any process that can open /dev/demo can overflow a kernel buffer with a long enough write. The read handler has the mirror-image problem: it copies one byte and returns count, so it tells its caller it produced as much data as was asked for regardless of what it produced. The GPIO read helper is declared as returning a pointer and returns nothing on its successful path.

The module is loaded and unloaded around every request

Each click runs insmod, switches four LEDs one at a time, and runs rmmod. Two overlapping requests fight over the module. It also exports its GPIO pins on load and never unexports them, so a second load hits pins that are already exported. Worse, the promise wrapping insmod logs its failure and returns without either resolving or rejecting, so if the load ever fails the request does not error, it simply stops existing.

A page held together by an early return

The browser page's timer function ends by assigning an undefined variable to the output element, which would throw on every call. It never throws, because a hidden text input that nothing ever fills keeps a validation check at the top of the function returning first. The page works because of a bug in front of a bug. There are also three separate <head> elements and a script tag pointing at the server's own source file, which 404s on every load without consequence.

Credentials in the source

The notification feature is five percent of the grade and our report records it as not working. What it left behind is a mail transport with a university address and its password sitting in plain text in the server file, in two files rather than one, because the working copy had been pasted into the page server as well. That is the kind of thing a second copy does: it doubles the mistake and halves the chance of finding it. Both read the environment now, and an account password was the wrong secret to have used in the first place, where an app password could have been revoked on its own.

Key Engineering Learnings

  1. Check that the indicator can fail. The hazard LED lit during the demo, so nobody looked further. It cannot light for the example printed on the assignment sheet, and one question would have found that: what input makes this lamp stay dark when it should not? Testing that a signal appears is not testing that it means anything.
  2. Ordering can be a design decision, and it should be written down. The pipeline works because four blocks appear in one order rather than another, and nothing in the file records that. An invariant nobody can see is an invariant somebody will break.
  3. A name on a layer is not evidence of what the layer does. The thing called a driver reached back up to sysfs and asked user space's interface to do the work. Reading what a component actually does, rather than what its name promises, is most of what a code review is.
  4. When a constant lives in three files it will drift, and the fix will land in the wrong one. Four LED numbers, three orderings, and a permutation table in the web server compensating for wiring nobody corrected. Duplication does not cause the bug; it decides where the bug gets patched.
  5. An interface that reports what it asked for is not an instrument. Both semesters ended with a display driven by the code that issued the command. The only path that read the hardware back sent its answer to a log nobody watched, which is how a system passes a demo and tells you nothing about whether it works.
