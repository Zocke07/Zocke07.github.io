Built in a Week, Audited After the Fact

For a fifty-person Advent retreat run by an Indonesian Catholic community in Taiwan, participants needed somewhere to read the notes of encouragement others left them, and anyone needed a way to leave one without signing it. I built it in the week before the event: pick your name, type the last four digits of your phone number, read your inbox; or skip the login and write to someone anonymously. It did its job for the event. Reading it again afterwards, the way I would review someone else's code, turned up four problems. This page is those four, and what fixing them took.

My role: sole developer, on a one-week deadline, with nobody reviewing the code. The fixes described here came after the event, on a separate branch, and three of the four are pinned by a test.

  • 50 participants, one event
  • 7 commits in one week
  • 6 API routes on Express
  • 4 problems found in review
  • 10 tests, no new dependencies
  • 0 phone numbers sent to the browser
Privacy, and where the numbers come from: no participant's name, phone number or message appears on this page, and the screens are described rather than shown. The code is not linked: the roster was committed during the event week, and although new commits no longer carry it, it is still in the history, so the repository stays private. Every figure here comes from the code and its tests.

What It Had to Do

The constraints came from the event, not from engineering. Nobody creates an account for a weekend retreat, so there could be no sign-up. The organizers already had a roster from their registration form, with a name and a phone number for each participant, and that roster became the login: choose your name from a list, then type the last four digits of your number. Leaving a note needed no login at all, because the point was that the sender could stay anonymous.

The server is Express on Node.js, serving five pages and six JSON routes. Messages went to Supabase, a hosted PostgreSQL, because the hosting it ran on wipes its disk on every restart, and a note that disappears overnight is worse than no note. A migration script moved anything already written to the local JSON log into the database in batches, with a dry run first, so nothing written before the switch was lost.

One decision held up under review. The participant list the login page needs comes from a route that returns each person's id and name and nothing else, so the phone numbers the login checks against never leave the server.

Notes were parsed as HTML

The inbox built each note with innerHTML, dropping the sender's display name and the message straight into a template. Both came from whoever wrote the note, signed in or not, so a note containing markup was parsed as markup in the recipient's inbox.

The damage was smaller than it sounds, and the reason is worth knowing. The server sends a Content-Security-Policy header that forbids inline scripts, so a note carrying <img onerror=…> would not run when the pages came through Express. A header is a backstop, though, not a fix: markup could still restyle or fake parts of the page, and anywhere the header is missing, the same note would run as script and could read the session token the browser keeps.

Four digits guarded a name anyone could see

The secret was the last four digits of a phone number: 10,000 possibilities, for a name the login page lists. Nothing limited the attempts, so a short loop could try every combination for one person and read their notes.

Sessions lived in one instance's memory

A successful login stored a token in an in-memory map. That works on one long-running server and fails on serverless hosting, where each instance has its own memory: a login handled by one instance was unknown to the next, and every cold start logged everyone out. The project included an entry point for exactly that kind of host.

Inboxes were matched by name

A note was saved with its recipient's name, and an inbox was every note whose recipient matched yours after lowercasing. The roster already gave each person a unique id, but notes never used it, so two participants with the same name would have read each other's notes.

What Each Fix Does

Notes and names are now put on the page with textContent, so the browser treats them as text. A note containing <img onerror=…> now shows its recipient exactly those characters.

Login attempts are counted. Five wrong guesses lock a name for fifteen minutes, even against the right digits, and one address gets twenty attempts in the same window. A locked request gets a 429 with a Retry-After header saying when to try again.

Sessions are now signed instead of stored. A token carries the participant's id and an expiry, followed by an HMAC of both, computed with a secret only the server holds. Any instance with the same secret can check a token another instance issued, and changing one character of the claims breaks the signature. 

// Checking a token: recompute the signature, compare in constant time.
const expected = Buffer.from(this.#sign(payload));
const given = Buffer.from(signature);
if (given.length !== expected.length || !crypto.timingSafeEqual(given, expected)) {
  return null;
}

timingSafeEqual takes the same time however much of the signature matches, so the check reveals nothing about how close a guess came.

Notes now store the recipient's id, and an inbox matches on it. The wrinkle was the live database: its table has no column for the id, and code that writes a column the table lacks makes every insert fail. So the column is opt-in. Until it is added and switched on, notes work exactly as before; after, new notes reach their recipient by id, and only notes written before the change still match by name.

The roster, the registration responses and the message log are out of version control, with an example roster of made-up people for local development. On hosting with no disk, the roster can be supplied as configuration instead of a file.

What the Tests Pin Down

Ten tests run on Node's built-in test runner, with no new dependencies. Each one starts the real app on a free port, with a temporary folder holding a made-up roster, so nothing touches the event's data or the database.

Three of them check what the review found. Two people with the same name get separate inboxes. Five wrong guesses for one name lock it, after which even the right digits get a 429. A token whose claims were rewritten to someone else's id, still carrying the original signature, is rejected.

One gap is worth naming: the rendering fix is checked by reading the code, not by a test. The tests confirm a note comes back from the server exactly as it was sent; whether the page then shows it as text depends on code that only runs in a browser, and there is no browser in this suite.

What It Still Does Not Do

The counters behind the login and message limits live in each instance's memory, so on serverless hosting every instance keeps its own count and a restart clears them. That turns an unlimited guessing loop into a slow one; a shared limit needs a table in the database.

Logging out revokes a token only on the instance that handled the request. Everywhere else it stays valid until it expires, twelve hours after login.

Four digits are still four digits. The limits make guessing slow; they do not make the secret strong. The real fix is a code per participant, handed out at registration, which needs the organizers rather than a commit.

And the roster is still in the repository's history. New commits no longer carry it, but anyone with access to the history could read it, which is why the code stays private and is not linked from this page.

Key Engineering Learnings

  1. Review your own code after the deadline is gone. Every problem here was visible in the original diff. What the event week lacked was not skill but a second read, and the cheapest second reader is yourself, later.
  2. A security header is a backstop, not a fix. The Content-Security-Policy kept an injected script from running. It did nothing about why one could be injected, and it only protects the pages that actually carry it.
  3. Serverless changes what in-memory state means. A map in the process is shared state on one server and private state on many. Sessions and rate limits both had to be rethought for it, and only one of them could be fixed without a database.
  4. A schema change cannot ride along with a code change. Code that writes a column the live table lacks breaks every insert the moment it deploys. Making the column opt-in let the fix ship first and the migration follow when someone runs it.
  5. Data you need to run is not data you need to commit. The roster had to be on the server. It never had to be in git, and once it was, deleting the file was no longer enough to take it back.
