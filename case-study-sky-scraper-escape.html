Case Study · C++ & Object-Oriented Design · University Project

The Menu Is Just Another Level

The assignment was a game with seven levels, each one different. The teaching framework underneath it allowed exactly three states, forever, by design. Reconciling those two numbers turned out to be the entire project, and the answer we arrived at was a base class that made every level and the menu screens into the same kind of object.

My role: I wrote most of the team's game code, including the level base class, the player, the menu system, and levels one, five, and six. My teammate wrote levels two, three, four, and seven and the obstacle-spacing algorithm. This is a university project, so unlike my other case studies I can show you the code.

  • 7 levels behind one interface
  • 2,237 lines of C++ we wrote ourselves
  • 76% of them written by me
  • 17 merged pull requests
  • 3 months, March to June 2024
  • 1 pointer in the main loop

Where the numbers come from: this was a two-person project, so I checked my own claims against git blame rather than memory. The counts cover Source/Game, the directory holding the code we wrote, with the framework's imported template files excluded from my share. Everything under Source/Library and Source/Core is the teaching framework and is not ours. The repository is public.

The Problem

The course supplied a Windows game framework written for teaching. It gives you a fixed-size table of three game states, an init screen, a run screen, and a game-over screen, and an abstract CGameState with eleven virtual methods on it: OnMove, OnShow, OnKeyDown, and the rest of the input handlers. The framework's own loop calls those methods on whichever state is current. You cannot add a fourth state. The table is declared as CGameState *gameStateTable[3] and the framework says so in a comment.

Seven levels do not fit into three states. The obvious move, the one I started with, is to put the levels inside the run state and branch on a level number. That works for two levels. By level four you are writing the same switch in eleven different event handlers, every new level means touching all of them, and the run state has become a file that knows every rule in the game.

What made it worse was that we did not know what the later levels would need. Level five hides its obstacles on a timer. Level six moves them vertically. Level seven inverts gravity. None of that was designed up front. Whatever we built had to absorb mechanics we had not thought of yet without the run state growing a branch every time.

The Design

The framework was already doing the thing we needed, one layer up. It holds a pointer to the current state and forwards events to it, and it never asks which state that is. So we copied the idea down a level: a base class, levelInit, declaring the same methods the framework's CGameState declares. The comment I left above them is still there, and it is the whole design in three words: imitates mygame_run functions.

Once every level implemented that interface, the run state stopped being a dispatcher and became a holder. It owns one vector of base-class pointers and one pointer to the current element.

// mygame.h: every screen in the game, held as the same type std::vector<levels::levelInit*> allLevels = { &theMainMenu, &theLevel1, &theLevel2, &theLevel3, &theLevel4, &theLevel5, &theLevel6, &theLevel7 }; levels::levelInit* current = allLevels[currentLevel]; // mygame_run.cpp: the framework's events go straight through void CGameStateRun::OnKeyDown(UINT nChar, UINT nRepCnt, UINT nFlags) { current->OnKeyDown(nChar, nRepCnt, nFlags); }

Seven of the run state's eleven methods are exactly this: one line, forwarding, no branching.

The bottom row is the part the framework was never going to allow. Eight screens live behind one pointer of one type, so adding an eighth level is adding an element, not editing a dispatcher. The menu sitting at index zero is the test of whether the abstraction was real: if it had needed its own branch, the shape would have leaked.

The first element of that vector is the level-select screen. It is not a level, but it derives from the same base class, so it sits in the same array and is reached through the same pointer. That was not cleverness for its own sake. The menu needs a background, a keyboard handler, and a draw call, which is exactly what a level needs, and giving it a different shape would have meant a special case in the run state for the one screen that is not a level.

What the Base Class Owns

An interface alone would not have paid for itself. The base class also absorbed everything the seven levels genuinely share, so a new level file could be short.

The parts every level would otherwise rewrite

It holds the plane, the background, the explosion sprite, and the in-game menus, and it implements the behaviour that goes with them: applying the plane's movement each frame, drawing the background and the plane and the wreckage, and building the heads-up display text. A level that wants extra readouts overrides getText and appends to what the base class returned, which is how level five shows its countdown and level seven shows which way gravity is currently pointing.

The pause and game-over state machine

The single largest thing the base class took over is the menu logic: what the escape key does, what happens when you crash, what happens when you finish, and which of the pause, game-over, and congratulations pop-ups is on screen. That is sixty-five lines of nested conditionals in a single method, written once, and no level implements any of it. A level with a brand-new mechanic still gets a correct pause menu for free.

How a level tells the shell it is done

Levels never call the framework. They set flags, retry, nextLevel, toInit, chooseLevel, and the run state reads those flags each frame, clears the one it saw, and performs the actual state transition itself. This is polling rather than events, which is the less fashionable choice, and it is the reason a level file contains no reference to the framework's state machine at all. A level knows about gravity and buildings. It does not know it is inside a state.

Seven Twists, One Shape

Every level overrides three methods, OnBeginState, OnMove, and OnShow, calls the base class version first, and then adds only its own idea. The twists themselves are deliberately small. Most of them are one extra field and one extra method.

Level one, rebuilt from the game's own bitmaps at the coordinates level1.cpp actually uses: the plane at its start position of (180, 270), obstacle pairs whose gap is pathHeight minus fifteen pixels, and the building and cloud drawn from the same pair of images every level reuses. It is a reconstruction rather than a live capture, because the game is a Windows MFC binary and this was assembled from the source assets.

  1. City SkiesThe baseline. Twenty buildings and twenty clouds scroll leftward; passing one scores a point; touching one ends the run.
  2. Tight SpaceThe horizontal breathing room disappears. The next obstacle starts moving the moment the previous one is fully on screen, so they arrive back to back, and the opening steps up or down by a fixed forty pixels each time. The opening itself is wider than level one, which is the only reason it is survivable.
  3. Narrowed SightA full-screen bitmap is drawn on top of everything with white registered as its transparent colour, so only a circle of the city shows through. It is a mask, not a lighting model, and it costs one extra draw call.
  4. Speed SurgeObstacle speed steps up on a frame counter, and the spacing algorithm widens the distance between later obstacles whenever acceleration is switched on. It is the only level that sets the acceleration constant to anything other than zero.
  5. Flickering ObstaclesA countdown toggles a visibility flag, and the collision check reads the same flag, so an obstacle you cannot see cannot kill you. The HUD shows how many seconds until they return.
  6. Vertical MoversObstacles gain vertical motion on top of the scroll. Collision needed no changes at all, because it tests the sprites where they currently are rather than where they were placed.
  7. Gravity FlipOne boolean on the plane. Every physics branch is mirrored: fall becomes rise, the jump target is added instead of subtracted, and the floor check becomes a ceiling check. A timer flips it every few seconds.

The one that taught me the most is level six. Adding vertical movement to obstacles required no change to collision detection, because collision asks the sprites for their current position rather than trusting a position recorded earlier. That was luck as much as design, but it is the kind of luck you only get when state has one owner.

What I Got Wrong

The architecture held up. Plenty else did not, and the code is public, so there is no point pretending otherwise.

The base class shares state well and behaviour badly

Every level's OnShow repeats the same forty lines: loop the obstacles, test for a collision, award a point, check whether the level is finished, then decide which pop-up to draw. Line for line, no two of the seven copies differ by more than a handful. Each level even redeclares its own building and cloud vectors instead of inheriting them, so the one thing all seven provably have in common is the one thing the base class does not hold. It should have owned that loop, with each level supplying only its obstacles. I did not restructure it because extending was easy and restructuring was not, which is exactly how duplication survives a review.

The abstraction is named after the afternoon I made it

The base class is called levelInit. It does not initialise anything in particular. It is the level interface, and it should be called that. By the time this was obvious the name was in every level file, and renaming felt like a bigger change than it was. The last commit on the project is literally titled "Rename class to avoid confusion", which fixed a different name and not this one.

Time is measured in frames

Every timer in the game is a counter incremented once per update, and the countdowns shown on screen divide by thirty to display seconds. Nothing is expressed in real time, so gameplay speed is tied to how fast the loop happens to run on the machine it is running on. Nobody noticed during the course, because everybody ran it on the same lab machines.

The physics is not physics

The plane moves a fixed four pixels per frame in whichever direction it is currently going, and a jump is a target height it walks toward at that same rate. There is no velocity and no acceleration, so the arc is made of straight lines rather than a curve. It plays acceptably, which is why it survived, but calling it gravity is generous.

The dispatcher still knows what level it is on

The run state forwards every input and every update without asking which level it is talking to. Drawing is where that breaks down. It reads the level number three times: once to decide whether to start the background music, once to suppress the heads-up display entirely, and once to print that display in white on level three, because that level darkens the screen and black text vanishes into it. The first two are really asking "is this the menu", which the types already knew and could have answered. The third is a genuine per-level special case, sitting in the one place I claimed there would be none.

Key Engineering Learnings

  1. An interface is cheaper than a branch. Seven levels could have meant seven cases in each of eleven event handlers. Behind one base class it meant one vector and one pointer, and the run state never learned how many levels the game has.
  2. Copy the design you are already standing on. The framework drove its own states by holding a pointer and forwarding calls. Recognising that pattern and reapplying it one layer down was worth more than any individual feature I wrote that semester.
  3. Inheritance shares state easily and behaviour badly. Moving shared fields into a base class took an afternoon. The shared per-frame logic stayed copy-pasted across seven files, because adding a method is always easier than moving one.
  4. Name an abstraction after what it is, not when you created it. A class called levelInit that is really a level interface will be misread by every person who opens the file, including the person who wrote it, six weeks later.
  5. The most useful thing I built was the way to skip my own game. A debug key disables collision so a level can be played to the end without dying, because otherwise testing level six meant surviving level six first. I called it cheat mode. What it actually was is a test hook, and it is the first one I ever wrote without being asked.
