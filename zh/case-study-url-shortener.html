一個短連結，兩次寫入

短網址服務是最小的、卻仍然得回答一個真實設計問題的服務：短碼從哪裡來？把網址拿去雜湊，就等於自己請來了碰撞，以及一整套解決碰撞的機制。這一套的做法是拿 MySQL 為那一列發出的 id，把它編成 Base62，於是碰撞在結構上就不可能發生，而建立一個連結變成兩句 SQL 的事，因為衍生自那一列的短碼，在那一列存在之前算不出來。

我的角色：一個沒有團隊、也沒有人出題的個人專案，而這件事是雙面的：沒有東西是別人交到我手上的，也沒有東西經過別人審查。這個服務小到每一個決定都得拿出理由，而不是從框架的預設值裡順手收下，這正是這一頁在談的事。最值得讀的一段，是 Spring 的一個便利功能悄悄蓋掉了 schema 早就宣告好的欄位預設值。

  • 2 個端點，一個建立、一個跳轉
  • 6 個類別，分成四層
  • 1 張表、4 個欄位、1 個索引
  • 建立一個連結要 2 句 SQL
  • 4 個測試，3 個單元、1 個整合
  • 短碼字母表共 62 個字元
範圍，以及數字的來源：這個服務刻意做得很小。兩個端點、一張表，而一個正式上線的短網址服務接下來需要的東西，像是擋在跳轉前的快取、離開請求路徑的點擊分析、流量限制、多台主機，都放在最後當作取捨來談，而不是做出來。這一頁引用的每一個狀態碼，都是對著跑起來的服務、連著本機 MySQL 量到的，而不是抄自 README；而這兩者唯一對不上的地方，下面寫成了它本來的樣子：一個缺陷。原始碼是公開的。

整份契約，就兩個端點

一個端點替網址建立短碼，一個端點把短碼帶回原網址。沒有帳號、沒有後台、也沒有刪除，而這個介面刻意維持在這麼小：這兩個之後的每一個功能，能買到的都比替這兩個辯護所花的時間還少。 

$ curl -s -X POST localhost:8080/api/v1/urls \
    -H 'Content-Type: application/json' \
    -d '{"url": "https://spring.io/projects/spring-boot"}'
{"code":"5"}

$ curl -sI localhost:8080/5
HTTP/1.1 302
Location: https://spring.io/projects/spring-boot

不存在的短碼得到 404。其他什麼都沒有定義，而這正是先把契約寫下來、再寫 schema 的用意。

這兩個呼叫的背後是四層，而把它們分開的理由是：這樣每一層就只需要知道一件事。controller 知道 HTTP，service 知道規則，repository 知道 SQL，而整個設計所倚賴的那個 id，在資料庫說出來之前只有它自己知道。

短碼來自它所指向的那一列

最直覺的產生方式，是把網址雜湊之後截短到可以打得出來的長度。它只要一句 SQL、不需要保存狀態，而它錯在一個要很久以後才會現形的地方：雜湊值截得夠短，兩個不同的網址遲早會產生同一個短碼。那不是一個你可以選擇不要有的錯誤，而是一條你得寫出來、測出來，然後在每一次寫入都付出代價的分支。

另一條路，是去編碼一個本來就唯一的東西。MySQL 會替每一列發一個唯一的 AUTO_INCREMENT id，所以短碼可以就是那個數字寫成 62 進位，用上數字、小寫字母和大寫字母。一個唯一數字的 Base62 之所以唯一，是因為這個編碼是一對一的映射，不是因為誰去檢查過。沒有碰撞處理要寫，因為根本沒有碰撞要處理。

代價立刻就來。如果短碼是 id 的函數，而 id 是那句 INSERT 發出來的，那短碼就不可能是同一句 INSERT 的一部分。於是建立一個短連結是兩句 SQL，不是一句。

編碼本身是一個迴圈，裡面有兩件很容易被混在一起的工作：餘數負責挑字元，除法負責把數字縮小到下一輪。它是從最低位往上把字串疊出來的，所以每個字元是插在最前面，而不是接在後面。 

// 0 -> "0", 61 -> "Z", 62 -> "10", 63 -> "11"
StringBuilder code = new StringBuilder();
while (counter > 0) {
    code.insert(0, ALPHABET.charAt((int) (counter % BASE)));
    counter /= BASE;
}

62 個字元用六位就有四十億種短碼，遠比這個服務用得到的還多，也比一個 UUID 短得多。

一張表，以及每個欄位得自己掙來的位置

CREATE TABLE urls (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    short_code  VARCHAR(10)   UNIQUE,
    long_url    VARCHAR(2048) NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

主鍵是 id 而不是 short_code，即使對外界來說短碼才是那個會被用到的東西。鍵應該是一個沒有意義、但穩定的把手，而不是某個之後的決定就能改掉的業務資料：換掉產生器，每一個短碼都會變，而任何指著短碼的表就會指向空的地方。實務上它同時也是編碼器需要的那個數字，所以這個代理鍵一次賺回兩份。

short_code 是 UNIQUE，而在 MySQL 裡這也順手建出了跳轉查詢會用到的索引，所以一個關鍵字同時買到保證和查詢計畫。它沒有的是 NOT NULL，而這個「沒有」就是上面那張圖在 schema 裡現身的樣子：在 INSERT 的那一刻，短碼真的還不存在。MySQL 允許唯一約束底下有多個 null，所以對已經有短碼的那些列，什麼保證都沒有被削弱。

這個約束到底是為了什麼，值得說清楚。它不是唯一性的機制，因為自增 id 的 Base62 編碼本來就產生不出重複值。它是留給未來應用程式錯誤的一張安全網：如果哪天有人把產生器換成一個會重複的東西，資料庫會直接拒絕這次寫入，而不是安靜地讓一個連結指向兩個目的地。

long_url 完全沒有索引，這是最容易被質疑、也最好辯護的一個決定：這個服務裡沒有任何地方會查 WHERE long_url = ?。索引不是白拿的。它在每一次寫入都要付出寫入速度和磁碟空間，而只有在真的有查詢用到它的地方才賺得回來。重複的網址在這裡也沒關係。兩個人縮同一個網址會拿到兩個短碼，而把它們合起來只對這個服務沒有的功能有意義。

明寫的 NULL，不等於沒寫的欄位

created_at 宣告成 DEFAULT CURRENT_TIMESTAMP，而每一列讀回來都是 null。schema 是對的，那句 INSERT 也沒有提到這個欄位，資料卻還是錯的，而這正是讓一個錯誤難以被看見的組合：沒有任何一段可以讀的東西看起來是錯的。

原因是一個便利功能。Spring 的 SimpleJdbcInsert 只拿到一張表、其他什麼都沒給的時候，會去檢查那張表所有的欄位，然後替每一個沒有拿到值的欄位明寫一個 NULL。SQL 是在語句「省略」某個欄位時才套用預設值，而不是在語句寫出那個欄位、並把它設成 null 的時候。嚴格說，預設值從來沒有被跳過：它是被一個應用程式自己都不知道送出去的值推翻的。

要找到它，得放棄讀應用程式，改成去讀資料庫。MySQL 的 general_log 會記下一條連線送出去的原始 SQL，這把「這段程式大概做了什麼」的爭論，換成了一行寫著它到底送了什麼的文字。修正只有一個呼叫，把那次寫入釘在它唯一有值的那個欄位上： 

this.insertUrl = new SimpleJdbcInsert(jdbcTemplate)
        .withTableName("urls")
        .usingColumns("long_url")          // 整個修正就是這一行
        .usingGeneratedKeyColumns("id");

在這之後寫入的每一列，都帶著 schema 一直說它們會有的那個時間戳記。

比修正本身更值得帶走的是那條通則。預設值是語句的性質，不是表的性質；而任何一層替你產生 SQL 的東西，都在替你決定那句語句的形狀。只要它產生的正好是你自己會寫的，那沒問題。它不再沒問題的那一刻，是它比你更周到的時候。

用 302，因為 301 是一個只能做一次的決定

跳轉要挑一個狀態碼，而 301 是那個聽起來對的：目的地確實是永久的。它同時也是瀏覽器有權快取的那一個，也就是說，同一個短連結的第二次點擊，根本不會再回到這個服務。每一次計數、每一個來源、每一份「這個連結正在被用」的證據，都沒了，而且是安靜地沒了，因為一個被快取的跳轉看起來和一個正常運作的跳轉一模一樣。

302 放棄了那個好處，換來一次來回。每一次點擊都會回到伺服器，代價是每次點擊多一點延遲，換到的是「將來還有機會知道這些點擊的任何事」這個選項。這裡值得誠實說出這筆交易的大小：今天這個服務並沒有在計算任何點擊。這個狀態碼買的不是一個功能，而是不把一個功能提早關掉；如果分析這件事被永久排除，那 301 才是比較好的答案。

測試證明了什麼，又只是看起來證明了什麼

三個單元測試跑在一個被替換掉的 repository 上，所以完全沒有資料庫參與：建立一個短碼並解回原網址、拒絕空白網址，以及對不存在的短碼回傳 null。那個假物件只換掉資料庫這個邊界，其他什麼都沒換，而這個細節正是第一個測試值得跑的原因。Base62 編碼器並沒有被替換，所以斷言 id 62 會產生短碼 "10"，跑的是真正的邏輯，不是一個事先塞好的答案。

空白網址那個測試是我最想替它辯護的一個，因為它的第二個斷言。 

assertThrows(IllegalArgumentException.class, () -> service.createShortUrl("   "));

// assertThrows 只證明了某個地方丟出了例外。
// 這一行證明的是：它發生在守衛條款真正的工作，也就是
// 把垃圾擋在表外面，還來得及被繞過去之前。
verifyNoInteractions(repository);

把第二行刪掉，這個測試在一個「先寫入那一列、之後才失敗」的服務上照樣會通過。

第四個測試是披著同一個註解的另一種生物。產生器生出來的 contextLoads 會把整個 Spring context 啟動起來，也就是說它會開一條真的連線，並且在 MySQL 容器沒跑的時候失敗。它是一個整合測試，而有用的不是「四個」這個數字，是能講清楚這四個裡哪一個需要資料庫、以及為什麼。

它沒有做到的事

空白或缺少的網址會在 service 層被擋下來，在任何東西碰到資料庫之前，而這個守衛是有效的：一次被拒絕的請求之後，表沒有任何變化。少的是最後一步。沒有任何東西把 IllegalArgumentException 翻譯成狀態碼，所以呼叫端拿到的是 500，而誠實的答案是 400。修正是一個 @ControllerAdvice 處理器，而它沒有被寫出來。

在寫這一頁之前，README 宣稱的是那個 400。拿它去對跑起來的服務量一次，才把一份寫好的契約變回一個缺陷，而這也是這一頁每一個狀態碼都來自一次請求、而不是來自文字的原因。

它也完全沒有檢查那個字串是不是一個網址。"definitely not a url" 會被接受、被存起來，並且拿到 200 和一個可以用的短碼。失敗被延後給了點下去的那個人，他會從一個當初收下這個值時毫無異議的服務手上拿到 500。修正是在邊界做驗證，而有意思的是錯誤浮現的位置：送出壞請求的人，不是付出代價的那個人。

短碼在結構上也是猜得到的。編碼一個計數器，意味著 /1、/2、/3 就能照順序走完整張表，所以這裡的短連結並不是私密連結。這是「讓碰撞不可能發生」而不是「讓碰撞不太可能發生」所付出的價錢，而只有在這些連結後面沒有任何東西需要不被列出來的時候，這筆交易才划算。

除此之外：跳轉前面沒有快取，所以每一次點擊都是一次資料庫讀取；沒有點擊分析，而那正是 302 存在要保留的可能性；沒有流量限制；只有一台主機；還有開發用的密碼就放在 application.properties 裡，這對一個用完就丟的本機容器沒問題，放在任何真正該放秘密的地方都不對。

關鍵工程收穫

  1. 寧可選一個沒有失效模式的設計，也不要選一個有好處理器的設計。截短的雜湊需要碰撞偵測、重試路徑，還有兩者的測試。編碼一個本來就唯一的數字則一個都不需要，而代價付在一個顯眼得多的地方：那次寫入裂成了兩半。
  2. 預設值是語句的性質，不是表的性質。欄位預設值填的是語句沒有寫出來的欄位。把那個欄位寫出來、設成 null，預設值就被推翻了，而這正是一個熱心的驅動程式替我做的事，直到我去讀它真正送出去的 SQL 為止。
  3. 當程式和資料說法不一致，就去讀線路上的東西。應用程式說它只寫了一個欄位，資料說不是這樣。MySQL 自己的日誌一分鐘就把這件事定案了，而再怎麼重讀那些 Java 都不會。
  4. 守衛條款的價值，等於它擋下了什麼。斷言例外被丟出來，對「什麼時候」一個字都沒說。斷言 repository 從來沒有被碰過，才把這個檢查釘在邊界上真正有保護到東西的那一側。
  5. 連 README 也要測。它寫著一個這個服務從來沒有回傳過的 400。文件恰恰是在沒有人重跑的地方漂走的，而端點契約是最不該讓它漂走的地方。
