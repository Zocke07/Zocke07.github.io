在程式碼與人之間

六位實習生，分處兩個國家，為一家大型電信公司開發兩項內部 AI 產品。這是一支新團隊，沒有配置 QA 工程師，最需要自動化測試的那項產品也沒有測試套件；程式碼中更有相當比例是在 AI 協助下寫成的，因此不管實際能不能運作，看起來都很合理。總得有人判斷每一項變更到底什麼時候才真的算準備好，這就是我的工作。

我的角色：一半是遠端團隊的技術專案管理者，一半是在其他人必須信任這個東西之前，先親自把它測過一遍的人。我負責協調工作、掌管驗證關卡，並為另外兩項內部專案撰寫自動化程式。產品本身則是整個團隊的成果。

  • 6 人的分散式團隊
  • 完成 2 項內部 AI 產品
  • 約兩個月內 ~40 項規格化變更
  • 這些變更共 300+ 條書面驗收條件
  • 規格驅動的交付，先提案再寫程式
  • 發布前親手驗證並簽核
關於保密：本文遵守我對雇主的保密義務。內部服務名稱、主機名稱、端點、規範文件與商業邏輯皆已省略或改以概括方式描述，留下來的是在任何公司都不陌生的工程實務。規模數字描述的是團隊整體產出，我個人的貢獻則會明確標示出來。

問題

實習生團隊是一種很特別的工程單位。每個人能力都不差，但沒有人有脈絡，而能回答問題的人又都忙著自己的工作。我們的團隊還分處兩地，這代表化解誤解最便宜的方式，也就是轉過頭去直接問一句，根本用不上。

兩項產品都高度依賴大型語言模型，而且有很大一部分程式碼是在 AI 協助下寫出來的。這樣的組合會帶來一種特定的失效模式：AI 寫出來的程式碼可以編譯、讀起來乾淨、也通過審查，卻會以一種很有自信的姿態出錯，而且只有對上真實系統時才會現形。型別檢查抓不出一段悄悄弄丟超連結的翻譯；程式碼審查也抓不出預覽窗格顯示的是一個結果、實際寫回正式紀錄的卻是另一個。

所以真正的問題不在於把功能寫出來，而在於建立足夠的流程，讓六個人能朝同一個方向前進；以及建立足夠的驗證，讓我們分得出「看起來寫完的程式碼」和「真的寫完的程式碼」。

我們做了什麼

兩項產品，都是把語言模型包進一套工作流程裡，讓大家能在早就開著的工具中真的用起來。

  • AI 程式碼審查助理

    內部 IDE 擴充套件

    一套內建於編輯器的 AI 程式碼審查助理。它會讀取你正在處理的程式碼，收斂到值得檢查的區段，依組織自訂的開發規範進行檢查，並直接在有問題的那幾行上回報結果。

    底層架構：TypeScript 擴充套件主體與 React 側邊欄之間，以完整型別化的訊息橋接串接；一層 provider 抽象讓模型供應商可以替換；以語法樹解析精簡送出的內容；掃描結果採用經 schema 驗證的 JSON；並在工具送出的所有內容上加了一層淨化處理。

  • 在地化助理

    瀏覽器擴充套件

    一套嵌在內部內容編輯入口旁的翻譯流程。它會從頁面中讀出原始內容，以串流方式把譯文送進預覽區，再透過頁面本身的編輯器，把核可後的版本寫回去。

    困難的地方在邊界。一個完全不動到宿主應用程式的 Manifest V3 擴充套件，必須讓圖片與行內標記在整趟翻譯來回之後仍然完好，並確保審核者核可的內容和實際寫回去的內容一模一樣。

驗證關卡

在地化工具沒有自動化測試套件，因此「完成」需要一個不取決於作者自我感覺的定義。我們採用規格驅動的工作流程，而我把它落實成發布關卡。每一項變更都走同一套流程，最後一步沒過就不發布。

  1. 書面提案與設計要解決什麼問題、採取什麼做法、有什麼取捨。在寫程式之前先取得共識，遠端審查者才不必從 diff 反推當初的意圖。
  2. 以明確 WHEN/THEN 形式撰寫的驗收條件包含各種異常路徑：逾時、極端輸入、供應商失效，以及明訂的迴歸測試底線。
  3. 依編號任務清單進行實作每一項都能單獨檢核，因此不必開進度會議，跨時區也看得到部分進度。
  4. 手動端對端驗證這一步由我親自負責。用真實瀏覽器對上真正在運行的執行個體，明確寫出測試目標、預期訊號與通過標準。
  5. 明確簽核，或把不簽核的決定記錄下來當我們選擇接受某個缺口或跳過某一輪驗證時，這個決定連同理由都會寫下來，而不是留給大家自行意會。

我們一再以為某個修正已經完成，結果並沒有：某條在隔離環境下運作正常的寫回路徑，一碰到真實編輯器就把超連結壓成純文字；一段較長的譯文則在送到頁面之前，就被模型悄悄截斷了。這兩件事在 diff 裡都看不出來，但實際動手用，一分鐘之內就一目了然。

在 IDE 擴充套件這邊，驗證的樣貌不太一樣，因為那裡做得出測試套件。有三個相依讓這件事變得棘手：即時的編輯器 API、真實的版本控制系統，以及不具確定性的模型。團隊把測試放進真正的編輯器執行個體裡跑，在磁碟上建立用完即丟的儲存庫來實際執行指令，並把模型換成 stub，讓結果具備確定性、執行起來也不花錢。審閱那套測試套件的過程，是我今天對於如何測試「看似不可測之物」的認識的主要來源。

讓六個人朝同一個方向

這份工作中屬於專案管理的那一半，主要是在模糊變成重工之前先把它消掉。用 Jira 追蹤 sprint 任務，讓現場工程師與遠端團隊共用同一份進度狀態。書面提案與設計這一步，則讓意見分歧在還很便宜的時候就浮上檯面，也就是停留在文件裡，而不是等到有人已經朝錯的方向做了一個星期之後。

我低估的一點，是這個角色有多大比例其實是在做翻譯，是人與人之間的那種翻譯。現場工程師握有遠端團隊看不到的脈絡，而遠端團隊踩到的問題，又從來傳不到能替他們解套的人耳裡。我所創造的價值有很大一部分，就是察覺到兩個人正各自很有把握地在講不同的事情。

不需要我在場也能跑的那一半

上面那道關卡之所以必須靠人工，是有原因的。在地化工具沒有自動化測試套件，而真正重要的那些缺陷，也只有親手驗證才攔得下來。這份工作的另一半，就是不讓這件事成為故事的全部。

我為另外兩項內部專案撰寫了自動化程式。一項是 Python 測試套件，從零以 PyTest 建置，針對某項內部服務的關鍵端點執行，完全依據 API 文件寫成：有哪些端點、每個端點吃什麼、回什麼、可能拋出哪些錯誤碼，以及少數幾個範例呼叫。那份文件就是全部的規格，所以套件裡的每一條斷言，都是那份文件許下的承諾——當測試變紅，不是服務錯了，就是文件錯了，而只有人能判斷是哪一個。

而這套測試最先需要的並不是測試本身。API 的酬載是編碼過的，在有東西把它解開之前，斷言根本碰不到回應的內容；我先寫了這一層，之後每一條測試都是針對解碼後的欄位撰寫，而不是針對傳輸格式。

另一項以 Java 撰寫，最初只是一次修正，後來衍生成同一項作業裡的三塊工作。每月的回饋發放由兩邊出資，一邊是我們，一邊是外部合作夥伴；原本就有一支 Jenkins 作業每月呼叫同事既有的一支 API 執行這項核對。那支 API 把檔名當成參數傳入，可能被指向錯誤月份卻仍拿到一致的結果；我把它改成直接從約定好的位置讀取檔案。加總的方式必須完全對齊既有的舊制計算方式，其中有一個業務規則要求排除在外的項目，所以我把這條公式明確寫進查詢裡。另外，這項核對也需要能自己跑、跑完還要讓人看得到結果：我建置了一支 Jenkins pipeline，仿照既有的另一支相關檢核作業改寫而成，觸發核對、並行執行數項檢查，並自動把結果建立成一張票。

兩者都稱不上亮眼，而這大致就是重點。書面關卡需要有人站在那裡；會自己跑的程式不需要，它所涵蓋的工作也就不再是工作。

主要工程收穫

  1. AI 協助產出的程式碼，需要另一種審查方式。它出錯時是很有自信的，而不是很明顯的。審查者的任務因此從「這段寫得好不好」轉為「它對上真實系統時，是不是真的做到它宣稱的事」，而這個問題只有實際跑過才答得出來。
  2. 先寫驗收條件，是成本最低的品質工具。以明確的 WHEN/THEN 形式寫下條件，會逼著異常路徑在設計階段就攤開來，那時候處理它們只要一個句子，而不是一次發布。
  3. 關卡要能說不，才算數。把我們接受缺口的那些時刻記錄下來，簽核才有意義，因為一個從來不會被保留的核可，本身不帶任何資訊。
  4. 分散式團隊為模糊付出的代價，是以天計，不是以分鐘計。當那個原本能回答你問題的人正在睡覺時，事先把意圖寫下來就不叫官僚。
  5. 當發布前的最後一道關卡，會改變你讀程式碼的方式。你不再問它是不是正確的，而是開始問自己要怎麼知道它是正確的，而後者才是更有用的問題。
