個人專案 · 資料庫系統 · PostgreSQL

資料庫可以說不的地方

校園創客空間把 3D 印表機、雷射切割機和 CNC 銑床借出去，靠的是牆上一張紙本登記表。那張表擋不住兩個人搶同一個時段，看不出來他們有沒有受過那台機器的訓練，東西晚還或壞了也留不下任何紀錄。我用一套三層式網頁應用程式和一個 PostgreSQL schema 取代了它，而整個專案最後收斂成一個問題：真正重要的那些規則裡，哪些資料庫可以自己擋下來，碰不到的那些又該怎麼辦？

我的角色：一個沒有團隊、也沒有人出題的個人專案，而這件事是雙面的：沒有東西是別人交到我手上的，也沒有東西經過別人審查。方法本身都是教科書上的。真正值得讀的是我原本沒有規劃的那部分：三個缺陷之所以浮出來，只因為分析跑的是真實的資料，而不是 schema。

  • 14 個關聯、5 個 view、21 個外鍵
  • schema 中宣告 28 條約束
  • 4 份 migration，從空資料庫依序套用
  • 對 13 個關聯做函數相依分析
  • 19 個畫面，涵蓋 19 個使用者故事
  • 種入 687 筆預約，分布在 85 位成員
範圍與說明：這個創客空間是虛構的，裡面每一個人也是。三個房間借用了北科大一棟真實建築的名字，只是為了讓場景有個可辨識的落點；除此之外，那棟建築、它的設備，以及任何真實的校園運作，都沒有被寫進這裡。種入的成員、罰款與證照資料都是為了打到特定的查詢分支而編出來的，這正是它們存在的目的。

紙本登記表守不住的三條規則

那張紙有三種失效方式，而每一種都是一條等著被寫下來的規則。兩位成員在同一個時段填上自己的名字，然後兩個人都出現了。沒有人記錄登記的人有沒有受過那台機器的訓練，所以工作人員只能憑印象確認，或者根本不確認。機器晚了兩天才還回來，然後什麼事都沒發生，因為沒有留下任何可以據以收費的紀錄。

所以這套系統存在的目的，就是守住三件事：一台機器的一個時段只能有一筆預約、沒有有效證照就不能預約，以及逾時或損壞要留下一筆可以收費的紀錄。schema 裡其他所有東西，都是為了服務其中之一而存在的。

有意思的地方在於，這三條規則的性質並不一樣。第一條是資料庫可以自己守住的區間排除約束。第二條橫跨五張表、而且取決於預約的時間區間，這是 CHECK 看不到的範圍。第三條是一段算術，但要有人點頭它才會變成一筆欠款。一條 schema 直接拒絕、一條它碰不到、一條它不應該替人決定。

為了一條約束而選這個資料庫

「同一台機器的兩筆預約不能重疊」這條規則，多數系統都寫在應用層：先讀出既有預約、判斷、再寫入。這中間讀和寫之間有一段競爭窗口，而當兩個人同時按下確認，你就是在那段窗口裡把機器弄丟的。PostgreSQL 可以把這條規則寫成資料表層級的約束，這也是它被選上的原因。 

-- 001_create_schema.sql: 唯一一條資料庫自己守住的關鍵規則
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE booking ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (
    equipment_id                  WITH =,
    tstzrange(starts_at, ends_at) WITH &&
  ) WHERE (status <> 'cancelled');

同一個時段的兩筆並行寫入不可能同時成功，不管應用層做了什麼、或忘了做什麼。

這六行裡有三個細節，每一個都是實機示範時一定會被問到的。用的是 tstzrange 而不是 tsrange，因為後者吃的是不帶時區的時間戳記，會把欄位型別拖到錯誤的方向。WHERE 子句則是讓已取消的預約把時段釋放出來的關鍵：少了它，那個時段會被永久卡住，而放棄預約的人自己也再也訂不回來。tstzrange 預設是半開區間，所以 14:00 結束的預約和 14:00 開始的預約並不衝突，而這也正是系統其他地方採用的定義。

這條約束還一次付出、兩次回收。為了執行它，資料庫會在 (equipment_id, tstzrange(starts_at, ends_at)) 上建一個 GiST 索引，而那正好就是可用時段查詢想要的索引。完整性的保證和查詢計畫是同一個東西。這不是憑空假設，而是拿一份重新種入的資料庫實際量出來的：這個查詢穩定落在大約 2 毫秒，比規格書的 500 毫秒預算寬鬆了大約 250 倍，EXPLAIN 也證實了每台機器的衝突檢查，走的正是這條約束建出來的 Index Scan。

那條沒有地方可以宣告的規則

整個專案真正吃重的是第二條規則：成員必須持有涵蓋該機器類別的有效證照，才能預約它。這條規則橫跨五張表、而且取決於預約的時間區間，所以在 CHECK 裡沒有容身之處；它又太重要，不能散落在剛好會執行到的那幾條程式路徑上。

在那之前還有一個解釋要先定下來：有效是指「什麼時候」有效？我採用嚴格的讀法：整段預約區間都必須有效，而不只是送出預約的那一天有效。證照週五到期的成員不能預約週六，也不能預約一段從週四開始、到週六結束的區間。寬鬆的讀法會讓人預約到一台他走進來時已經沒有資格操作的機器，那就違背了這條規則存在的意義。

資料庫這邊的貢獻是一個 view，而不是 trigger。它把那串走訪攤平成一個「成員、類別、有效區間」的關聯： 

-- 把整串走訪攤平成 (成員, 類別, 有效區間)
CREATE VIEW v_member_category_authorization AS
SELECT g.member_id, ca.category_id, g.certification_id,
       g.granted_at AS valid_from, g.expires_at AS valid_to
FROM certification_grant AS g
JOIN category_authorization AS ca ON ca.certification_id = g.certification_id;

預約交易於是只要一句查詢就能滿足這條規則：必須存在一列，類別對得上這台機器，而且有效區間涵蓋整段預約，也就是 valid_from <= starts_at AND valid_to >= ends_at。

用 trigger 會執行得更強硬，但文件價值更差。這個 view 用讀得懂的形式把規則寫在 schema 裡，預約交易是唯一套用它的地方，設備目錄也重用同一個 view 來算「我有沒有這台機器的資格？」那一欄，所以成員看到的答案和伺服器實際執行的判斷，出自同一份定義。

同樣的讀法還帶出兩個結果。證照會在領取設備時重新檢查一次，因為三月合法成立的預約，主人的訓練可能四月就過期了：櫃檯會拒絕交機，但預約本身不會被刪掉。而過期永遠不追溯，所以已完成的預約在其背後的證照到期之後，仍然是有效的歷史紀錄。歷史不會因為時間流逝而被改寫。

十四條規則，各自住在哪裡

schema 裡宣告了 28 條 CHECK 與 EXCLUDE 約束，以及 21 個外鍵，每個外鍵都寫明了 ON DELETE 行為。我給自己定的規矩是：只要能用宣告式表達的，就一定宣告出來，因為忘了檢查的那條程式路徑繞不過資料庫的約束。以下是這個分工，以及每條規則為什麼住在那裡。

商業規則、各自的內容，以及執行的位置

十四條裡的八條。上面五條繞不過去，下面三條則取決於包住它們的那個交易寫得好不好，所以每一條都只住在一個檔案裡。

下面那三條之所以在應用層，不是因為我偏好放在那裡。每一條都寫明了自己的理由：一條要查別的資料表、一條要跨表比較區間、一條需要彙總。這三件事 CHECK 都做不到。把理由寫在規則旁邊，後來證明比這個分工本身更重要，因為那是「一個寫明白的限制」和「一個習慣」之間的差別。

有一條規則是刻意不自動化的。歸還逾時的時候，系統會算出超時時數、依時費率提出一筆罰款建議，然後就停在那裡：由工作人員確認、調整或是不收。算術是機器的工作，收不收錢是人的。

讀資料而不是讀 schema 的正規化

十三個關聯都做過一次函數相依分析：候選鍵、相依關係，接著是 2NF 和 3NF，而且被排除的候選相依也一併寫出來，而不是直接斷言「已經符合」。其中十一個本來就在 BCNF。這不是運氣，而是關於前面設計的一項主張：全面使用代理鍵、把自然鍵保留成 UNIQUE、多值屬性在轉換成關聯之前就先拆成實體，這些做法讓遞移相依沒什麼地方好躲。

需要處理的那兩個，需要的處理方式並不一樣。在 equipment 裡，一台機器的產品型號決定了它屬於哪一類機器，所以 (manufacturer, model) 決定 category_id，但它完全不是鍵：二十台機器只帶了十五種不同的型號與類別組合，而四台 Prusa MK4S 印表機各自存了一份「MK4S 是 FDM 印表機」這個事實。這允許的異常是一次單列更新，把其中一台印表機改歸到「雷射切割機」類別而沒有任何東西會反對；在那之後，證照規則會要求這台機器需要雷射證照，而旁邊那三台一模一樣的機器需要的卻是 FDM 證照。這一段被分解成一個 equipment_model 關聯，而 migration 會在自己的交易裡重新驗證無損失連接，失敗就整個回滾。

另一個分解出來的表，本來就已經存在

第二個有意思得多。由預約衍生的罰款，一定是開給做那筆預約的人，所以在 penalty 裡 booking_id 決定 member_id。教科書上的 3NF 說：把這個相依抽成獨立的關聯。真的照做，你會得到 (booking_id, member_id)，而那是 booking 的一個投影：決定端和被決定端本來就住在同一張表裡，而且決定端就是那張表的主鍵。把它實體化出來，只是替 schema 已經握有的東西再複製一份。 

-- 004_normalize.sql: 把相依交給本來就握有它的那張表來執行
ALTER TABLE booking ADD CONSTRAINT booking_id_member_unique UNIQUE (id, member_id);

ALTER TABLE penalty DROP CONSTRAINT penalty_booking_id_fkey;
ALTER TABLE penalty ADD CONSTRAINT penalty_booking_member_fk
  FOREIGN KEY (booking_id, member_id) REFERENCES booking (id, member_id)
  ON DELETE RESTRICT;

就唯一性而言，那條 unique 約束是多餘的，因為 id 本來就是主鍵。但 PostgreSQL 要求先有它才肯接受複合外鍵，而那一個索引就是這次修正的全部代價。

由工作人員直接開立、沒有對應預約的罰款依然合法，而且不需要任何特別處理：只要有任何一個參照欄位是 null，預設的比對語意就會跳過檢查。這條約束剛好只作用在相依真的成立的那些列上。

誠實地說，penalty 並沒有被分解，嚴格來講它仍然停在 2NF，屬性也完全沒變。真正改變的是：3NF 想要防止的那個異常已經寫不進去了，而那本來就是目的。在這之前，這個相依在專案裡有四個地方用文字和流程去補：ER 模型、決策紀錄、一段欄位註解，以及種子腳本裡的自我檢查。它們沒有一個擋得住一次錯誤的寫入。

三個只有資料看得出來的缺陷

寫函數相依分析最直覺的做法，是讀 schema。我改成從種入的資料反推，而且每一條都用查詢驗過一次；這樣比較慢，但抓到了三個 schema 不可能顯示出來的缺陷。三個都屬於同一類：資料看起來是滿的，實際上卻是退化的，於是獨立的欄位和相依的欄位長得一模一樣。

  1. 一個讓兩個欄位在成員內部變成常數的產生器。重度使用者用 k % 20 挑出來，領取與否則用 k % 10 決定。因為 10 整除 20，這兩個判斷在同一位成員內部都是常數：每個重度使用者不是每筆預約都有領取、就是一筆都沒有，逾時歸還也是全有或全無。彙總欄位的總數看起來還是很健康。只有在活動總覽 view 裡才看得出來，那裡排名最前面的成員全都是零缺席、零逾時，而這比一個空欄位更糟，因為它經得起隨手一瞥。
  2. 每一列都相等的時間戳記。每一筆維修事件的通報時間都剛好等於停機開始時間，每一筆已結案事件的完成時間也都剛好等於停機結束時間。從這種資料推導相依關係，你會得出兩個根本不存在的互相決定關係，並且判定這張表違反 3NF。修正的方式是讓種子資料講三個更接近真實的故事：定期保養時發現的故障，停機比通報更早開始；先留在線上等待初判的故障，停機比通報更晚開始；而文書作業則可以在機器已經歸隊之後才結案。
  3. 由中國剩餘定理製造出來的二十列並列。「預約量高於全站平均的成員」這份報表回傳的資料，有很長一段是逐位元組完全相同的，預約數全都一樣。重度使用者用 k % 20 指派，篩選條件則是 k % 43 < 20，而 43 與 20 互質，於是這組配對是均勻的：每個重度使用者拿到的預約數完全相同。這種畫面截圖出來只會像是捏造的資料，而這個查詢真正要問的「誰是重度使用者」，一份排不出名次的名單也回答不了。改用加權陣列來取索引之後分布就正常了，這份報表現在回傳六列、六個不同的數字，一個並列都沒有。

第三個是我用別的方法絕對找不到的。算術本身合理、列數是對的、分布的形狀也正是種子註解所主張的那個形狀，缺陷在於重度那一端內部的變異數是零。schema 沒辦法告訴你，你的資料是碰巧一致的。

這也改變了我讀種子腳本的方式。為了把表填滿而寫的種子資料，產出的報表看起來很滿；從查詢反推著寫的種子資料，產出的報表會讓每個條件判斷的兩個分支都被走到，而只有後面這種，才讓一個退化有機會被發現。

我留下的冗餘，以及我沒有加的那條約束

schema 裡有四個冗餘活了下來，而把它講成毫無冗餘會是假的。其中三個是跨資料表的，這是 3NF 說不上話的範圍，因為 3NF 是定義在單一關聯的屬性之上。

那三個裡有兩個是快照，存在的理由正是為了讓歷史不能被改寫。證照核發紀錄自己存一份到期日，而不是從證照定義的有效月數推算，因為推算會讓一次對有效期的修改，回溯地把好幾年前發出去的證照全部作廢。領取紀錄自己存一份應還時間，而不是去讀預約的結束時間，因為應還時間是在交機那一刻定下來的，推算出來的版本會悄悄改掉一筆正在進行中的借用。把這兩個相依強制起來，schema 的正規化程度不會改變，但會變得更糟，而這比一次乾淨的分解更難寫進報告裡。

我沒有加的那條約束，反而是看起來最理所當然的一條。換證會產生一筆新的核發紀錄，取代舊的那一筆，而執行「取代」最自然的方式，就是用一條排除約束禁止同一位成員、同一張證照有兩段重疊的有效區間。但它同時也會讓人無法在到期之前換證，而那正是最常見的情況，也正是儀表板上那個三十天到期提醒想鼓勵的行為。它的缺席是一個決定，不是疏漏，而且是有寫下來的決定。

它做不到的事

session 是存在 API 行程內一個 map 裡的 bearer token。它撐不過一次重啟，而且除了像這樣的單節點專案之外，用在任何地方都是錯的。正確的做法是簽章 token 或共用的 session 儲存，而那還沒寫。

容器化的資料庫路徑寫了但沒有驗證過：開發用的那台機器沒有安裝 Docker，所以 compose 檔和它的初始化腳本一次都沒有真的跑起來過。真正跑得起來的是本機 PostgreSQL 那條路。README 裡就是這樣寫的，因為一個沒有人執行過的安裝步驟，不算是安裝步驟。

還有延長預約：這是唯一一個違背系統自身慣例的功能，它的實作是直接就地更新結束時間。這裡其他每一次狀態變更都是只增不改的。只有這一個會毀掉原本的區間，而且不留下它原本是什麼的紀錄，這也是我會最先重做的部分，用一個延長紀錄的實體來取代一次比較安靜的 UPDATE。

主要的工程收穫

  1. 依你輸不起的那條約束來挑工具。一條規則決定了要用哪個資料庫，而執行這條規則的約束，順手也建出了主要查詢需要的索引。把一個競爭條件變成 schema 層級的不可能，值得為它選一整套技術。
  2. 無法宣告的規則，仍然只能住在一個地方。這裡有三條規則橫跨的資料表比任何約束搆得到的都多。讓它們沒有走鐘的不是什麼巧思，而是位置：一個交易、一個檔案，以及一段寫明資料庫為什麼守不住它的理由。
  3. 把相依寫成文件，不等於把它執行起來。專案裡有四個地方都正確地描述了同一個冗餘。一次寫錯的 UPDATE 可以從這四個地方中間直接穿過去。取代它們的那條複合外鍵只有一行，而且沒得商量。
  4. 從資料推導相依，而不是從 schema。只讀 DDL 的話，會把兩個並沒有違反 3NF 的關聯報成違反，還會把一個二十列並列的結果當成發現寫進報告。資料是可以碰巧一致的，而 schema 沒有辦法告訴你這件事。
  5. 講清楚哪些部分你沒有跑過。沒執行過的 Docker 路徑、一個撐不過重啟的 session 儲存、一個違背模型自身慣例的功能，這些寫下來都比默默假裝它們能動更有用。代價是一段文字，而它是「一個限制」和「一個意外」之間的差別。
