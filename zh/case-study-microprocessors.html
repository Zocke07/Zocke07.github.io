從真值表到管線化 CPU

兩個學期，方向剛好相反。第一個學期用 VHDL 往上疊：起點是手工從真值表推出來的七條布林方程式，終點是 FPGA 上一顆四階段的管線化 CPU。第二個學期在 NVIDIA Jetson TX2 上往下走：從交叉編譯出來的執行檔，一路走到一個可載入的核心模組，直到使用者空間是靠寫入 /dev 來控制硬體。兩個學期都沒有做出任何產品。但我今天知道自己測試的軟體站在什麼上面，就是因為這兩個學期。

這一頁是什麼：它不是在主張這些成果屬於我。這些全部都是分組完成的，第一個學期兩個人、第二個學期三個人；與其在兩年後回頭去分誰打了哪一行，這篇寫的是把這些程式碼讀過一遍之後，它們到底做了什麼、為什麼會動，以及哪裡不成立。作業是課程的，我掛名的是這份理解。

  • 9 個 VHDL 實驗，從邏輯閘到 CPU
  • 1,290 行 VHDL，散在 37 個檔案
  • 218 行是管線化 CPU 本體
  • 4 個階段，而且是倒著寫的
  • 236 行核心 C，一個字元裝置
  • 期末專題裡用上 5 種語言
範圍與歸屬：這裡沒有任何一項是我獨力完成的。第一個學期那九個 VHDL 實驗是兩個人一組做的；第二個學期的一切，包括每一次實驗課與期末專題，都是三人小組共同完成、以小組名義繳交的。底下沒有任何一段是以「我的作品」提出的。為了寫這篇，我把兩個儲存庫重新讀過一遍，而不是憑印象寫，所以每一項說法都指得出一個我打得開的檔案，包括那些不好看的部分。兩半邊都是公開的：VHDL 在 Microprocessor-Based-Systems，嵌入式那學期在 Microprocessor-Based-Systems-Lab，還有 demo 影片，下面那張照片就是影片的其中一格。本頁所有示意圖都是照著原始碼重畫的，沒有任何一張是課程投影片。

兩個學期，兩個方向

微算機系統，2023 年秋天，是在 FPGA 板子上寫 VHDL：八個指撥開關輸入資料、八個輸入指令，一排 LED，還有六顆七段顯示器。微算機系統實習，2024 年春天，是一台 NVIDIA Jetson TX2，跑 Ubuntu 18.04 與 4.9 版的 Tegra 核心，旁邊擺著麵包板、五顆 LED、一顆光敏電阻，以及一顆 MCP3008 類比數位轉換器。

前一門課是累積上去的。每週的實驗都是用上週的檔案做出來的，最後一個就是一顆處理器。後一門課則是往下鑽的，從應用程式開始，結束在核心裡面。

  1. 七段顯示器解碼電路七條布林方程式，一個線段一條，全部是手工從真值表推出來的。第二個目標要三位數，於是同樣七條方程式被貼了三次，每個訊號名稱加上後綴，一個檔案裡二十一個輸出，完全沒有用到元件。
  2. 加法器與減法器八個一位元全加器用進位串起來變成八位元加法器，再用全減器做一次同樣的事。也是從這裡開始，那個解碼器不再被複製貼上，而是變成 package 裡的一個元件，用名字實體化。
  3. BCD 加法器二進位加法在十進位底下會得到錯的答案，所以每一位數都要判斷有沒有進位、或結果是否大於九，然後加六修正。每位數十六個全加器加上一條布林式，整個結構化寫到底。
  4. 簡易運算器先用兩個多工器、一個全加器和一個四選一輸出選擇做出一位元的切片，再用迴圈生成七份並把進位串起來。
  5. 萬用移位暫存器八位元，含清除、並列載入與方向選擇，寫成兩個迴圈：把每個位元往同一邊挪一格，再把序列輸入補進空出來的那一端。
  6. 狀態機標準的兩段式寫法：一個組合邏輯 process 決定下一個狀態，一個時序 process 負責更新。六個狀態、一個輸入。後面所有東西都是用這塊拼出來的。
  7. 回復式除法器把除法寫成八次迭代的狀態機：減掉位移過的除數，如果結果變成負的就加回去，並在商裡補零而不是補一。六個狀態，而且迴圈計數那裡到現在還留著一行註解寫 --7 or 8?。
  8. 簡易 CPU把除法器的狀態機升級成一個指令週期：擷取、讀 Rs、讀 Rt、運算、寫回，由一個步驟計數器推動。八個 opcode、四個暫存器，一次做一件事。
  9. 管線化 CPU同一組指令集，差別在四個階段同時在跑，而且需要還在管線裡的值的指令會直接被前饋，而不是等它寫回。218 行。

有一個細節一路活到最後。第一週那七條方程式現在還在期末專案裡，而且不是精神上的：逐字比對，它們就是同樣的算式，只是輸入訊號改了名字。 

-- lab1_1.vhd，這門課的第一個實驗：a 線段，直接從真值表抄下來
a  <= (X and not Y and not Z) or (W and X and not Y)
   or (not W and not X and not Y and Z) or (W and not X and Y and Z);

-- final/hex.vhd，最後一個實驗：同一條式子，改了名字
a1 <= (s2 and not s1 and not s0) or (s3 and s2 and not s1)
   or (not s3 and not s2 and not s1 and s0) or (s3 and not s2 and s1 and s0);

把 W,X,Y,Z 換成 s3,s2,s1,s0 之後，七個線段全部相符。這顆處理器的顯示路徑，就是這門課第一個實驗的成果，一個字都沒動過。

這件事講得漂亮一點，就是每學期都更靠近硬體一層。但更有用的版本比較窄，也比較難看：兩個學期最後都留下一個「被信任的程度超過它掙得的程度」的指示燈。在 FPGA 上，那是一顆對著作業說明書上的示範例子永遠不會亮的 hazard LED。在 Jetson 上，那是一個只會回報「我剛剛要求了什麼」、從來沒有回頭確認過結果的網頁面板。

管線其實是一種敘述順序

管線化處理器指的是四個階段在同一個時脈週期裡、對四道不同的指令同時運作，而每兩個階段之間都有一組暫存器保存前一階段的產出。用 VHDL 寫的話，你會預期那是四個訊號加四個 process。實際上它是一個 process 加四個變數，而它會成立的原因，是一個很容易看過去的順序技巧，我自己也是真的坐下來把檔案讀完才看懂。

VHDL 的訊號是被排程的：指派要等 process 跑完才生效。變數則是立即的：指派下一行就看得到。所以只要四個階段倒著寫，寫回擺第一、擷取擺最後，每個階段都會在它的前一階段還握著上一週期的值時把指令往前搬，而下一行敘述才會把那個值蓋掉。這些管線暫存器不是我宣告出來的硬體，而是四行敘述照著特定順序排列所留下的縫隙，根本沒有被宣告出來。 

-- PipelineCPU.vhd，精簡過：四個階段在檔案裡出現的順序
process(Clock)
  variable tmpIns1, tmpIns2, tmpIns3, tmpIns4 : std_logic_vector(7 downto 0) := "11110000";
begin
  if rising_edge(Clock) then
    --Write back
    tmpIns4 := tmpIns3;        -- 讀到的是 EX 在上一週期握著的值
    ...
    --Excution
    tmpIns3 := tmpIns2;        -- 到這一行 tmpIns3 才被換掉
    ...
    --Instruction decode
    tmpIns2 := tmpIns1;
    ...
    --Instruction fetch
    tmpIns1 := Instruction;
  end if;
end process;

把那四塊裡的任兩塊對調，這顆處理器就不再是管線化的了。而檔案裡沒有任何一行提到這件事。

至少板子對管線本身是誠實的。一個叫 ExcuteStatus 的四位元輸出接到四顆綠色 LED，一個階段一顆，由持有它的那個階段點亮，遇到氣泡就熄掉。用按鈕一道一道送指令進去，你會看到一顆亮著的 LED 沿著那一排走過去；連續送四道，整排就會全亮。它是一支四位元的管線佔用率追蹤，而且是這個實驗唯一的除錯工具。

那條本來就已經存在的前饋路徑

前後兩道指令碰到同一個暫存器，正是管線難做的原因。add r1, r2 要到寫回階段才把結果寫進去，而那時下一道指令早在兩個階段之前就把運算元讀走了。作業裡偵測這個衝突並用停頓解決佔百分之十，改用前饋解決再佔百分之十。所以這裡有一個偵測器。 

-- PipelineCPU.vhd，解碼階段裡，原封不動
if ((not(tmpIns3(3 downto 2) = "00")) and
    ((tmpIns3(3 downto 2) = tmpIns2(3 downto 2)) or
     (tmpIns3(3 downto 2) = tmpIns2(1 downto 0)))) then
  HazardDetection <= '1';
  tmpRs := excuteResult;
else
  HazardDetection <= '0';
  case tmpIns2(3 downto 2) is
    when "00" => tmpRs := r0tmp;
    ...

tmpIns3 是正在執行的那道指令，tmpIns2 是正在解碼的那道。第 3、2 位元是目的暫存器，第 1、0 位元是第二個運算元。

它驗收過了。明顯的衝突都會讓紅色的 hazard LED 亮起來，算出來的數字也對，在實驗桌上這樣就結束了。現在重讀，有兩件驗收看不出來的事情是成立的，而且方向剛好相反。

前饋在前一行敘述就已經發生了

這個設計裡有兩組暫存器檔，而看起來只有一組是刻意做的。訊號 r0 到 r3 在寫回階段被寫入，而除了七段顯示器之外沒有任何東西讀它們。變數 r0tmp 到 r3tmp 在執行階段被寫入，而那才是解碼階段真正讀的東西。因為在同一個 process 裡，執行階段寫在解碼階段上面，所以等下一道指令來找運算元時，這組影子暫存器裡早就放著前一道指令的結果了。不管偵測器有沒有觸發，資料路徑都會前饋，理由和整條管線會前進的理由是同一個：敘述順序。

這也表示那個 if 分支和 else 分支只是取同一個數字的兩種寫法。 excuteResult 和執行階段剛剛把它寫進去的那個影子暫存器，在結構上必然相等。偵測本身是真的，但它邀功的那個前饋，其實是檔案排版的副作用。

而在偵測器真的會改變答案的地方，它是錯的

那個條件在「執行中指令的目的暫存器」對上「解碼中指令的第一或第二個運算元欄位」時觸發，然後不管相符的是哪一個，都指派給 tmpRs，也就是第一個運算元。當衝突只發生在第二個運算元上時，這就等於把一個指令根本沒在問的暫存器蓋掉。 add r1, r2 之後接 add r2, r1，算出來的是新的 r1 加上它自己，再存進 r2。而 else 分支，也就是這個偵測器號稱要改良的那條路，本來會算對。

條件的第一項則是同一件外衣底下的第二個錯誤。not(tmpIns3(3 downto 2) = "00") 把 R0 排除在目的暫存器之外，因為氣泡被編碼成 11110000，它的目的欄位讀起來就是 R0。本意是「忽略氣泡」，但這個判斷是對著錯的四個位元寫的：一道指令是什麼，是 opcode 說了算，目的欄位從來就不負責這件事。代價是所有發生在 R0 上的衝突都不會點亮 hazard LED，包括 add r0, r1 接 sub r0, r2，而那正是作業說明書上印的示範例子。算術倒是照樣正確，因為影子暫存器檔並不在乎偵測器怎麼想。一個沒辦法回報「說明書上那個失效情境」的指示燈，就不算指示燈。

這是我寧可在 2023 年就想通的部分。當時 demo 會過，是因為驗的是「燈有沒有亮」，而不是「它是不是為了對的理由亮」；從那裡，到我現在工作中那個要分辨「綠燈的建置」和「只是看起來綠的建置」的部分，中間是一條直線。

從另一邊往下走

第二個學期從第一個學期蓋好的東西上方開始，然後一層一層往下穿過去。它的第一課是「編譯器不等於機器」：一支寫抽象形狀與排序的 C++ 程式，在一台電腦上用 aarch64-linux-gnu-g++ 編譯，拿到另一台上執行。這支程式本身沒有任何一點嵌入式的味道，但讓它跑起來的過程全都是。

  1. 交叉編譯多型的形狀類別加上一個排序，在筆電上編成 aarch64 的執行檔，拿到板子上跑。makefile 開頭第一行是 CROSS_COMPILE = aarch64-linux-gnu-。
  2. 從使用者空間控制 GPIO點亮一顆 LED 的做法是：open("/sys/class/gpio/export")、寫入接腳編號、往它的 direction 檔寫 "out"、再往 value 檔寫 "1"。四次檔案寫入，不需要任何函式庫。
  3. 把 GUI 疊在同樣那四次寫入上直接在板子上跑 Qt：核取方塊、綁定閃爍週期的滑桿、鍵盤快捷鍵，以及一個讓兩組 LED 輪流亮的 QTimer。
  4. 把瀏覽器疊在同樣那四次寫入上一台 Express 伺服器負責送出靜態頁面，並用子行程呼叫實驗二那支執行檔。控制介面從板子上搬走，搬到同一個網段裡任何一台有瀏覽器的機器。
  5. 一個位元一個位元地讀類比訊號數位接腳讀不了光敏電阻，所以由 MCP3008 負責轉換，而 Jetson 得自己把這段對話敲出來：先移出五個位元的命令，再打十二個時脈把結果移進來，整段交換的前後還要拉低與拉高晶片選擇腳。SPI 是用 Python 迴圈切換四條線做出來的。
  6. 讓瀏覽器把數值讀回來實驗四與實驗五接在一起：Express 伺服器同時用子行程呼叫驅動 MCP3008 的那支 Python，網頁再用 $.ajax 定時輪詢，而不是只問一次。回傳值一旦越過門檻，LED 就自己切換，不需要任何人點擊。這就是期末專題的縮小版，只是從四間房間變成一間。
  7. 進到核心裡一個註冊字元裝置的可載入模組，於是 LED 改成靠寫位元組到 /dev/demo 來切換，而不是寫 sysfs。

期末專題就是把這七層疊起來：一個叫 Smart Room Management 的會議室管理面板，四顆 LED 是四間房間，第五顆是預約計時器，走廊上的光敏電阻決定走廊燈需不需要開。在瀏覽器裡勾選房間、設定時間，被選到的房間就會在這段時間內閃爍。

那個什麼都沒驅動的驅動程式

核心模組佔專案分數的百分之二十，也是整份專案裡最像系統程式的一塊。它是 236 行 C，註冊了一個 major number 為 60 的字元裝置，並實作 open、read、 write、ioctl 與 release。把它載入、往 /dev/demo 寫四個位元組，就能切換一顆 LED。這些都是真的。

但它也不是驅動程式。以下就是它全部的協定和全部的機制： 

/* demo.c：write 處理函式的協定就只有四個字元寬 */
copy_from_user(userChar, buf, count);
userChar[count - 1] = '\0';
strncpy(gpio, userChar, 3);   /* "255" */
value[0] = userChar[3];       /* '1'、'0'，其他字元一律當成「讀回來」 */

/* 而這就是這次 write 最後真正做的事，從核心裡面 */
snprintf(buf, sizeof(buf), "/sys/class/gpio/gpio%s/value", gpio);
fd = filp_open(buf, O_WRONLY, 0);
vfs_write(fd, value, strlen(value), &pos);

外面還包著 set_fs(get_ds())，因為要讓核心在期待使用者空間緩衝區的地方接受一個核心空間的緩衝區，就得這樣做。需要這行呼叫本身就是味道。

這個模組沒有碰任何一個 GPIO 暫存器，也沒有呼叫 gpio_request 或核心 GPIO 介面的任何一部分。它打開 /sys/class/gpio/gpio255/value 並寫一個字元進去，而這正是四週前實驗二在使用者空間用大約十行做完的事。驅動程式存在的意義是當那個堆疊的最底層。這一個卻爬回它本該取代的那一層，然後請那一層幫忙做事。它多加了一跳，而不是少掉一跳。

這個實驗真正教的東西，值得跟它自稱在教的東西分開來講。它讓人看見字元裝置怎麼註冊、 copy_from_user 為什麼存在、major number 是幹嘛的，以及一個模組的編譯是怎麼被綁死在它要載入的那個核心上：這一個是對著 4.9.299-tegra 的標頭檔編的，而且在任何近代核心上都編不起來，因為 set_fs 和 vfs_write 早就被拿掉了，理由正是上面那段程式碼展示出來的東西。它沒有教的，是怎麼驅動硬體，而當時你問我，我會說我學會了。

評分標準蓋出來的系統

專題規範給驅動程式百分之二十、多執行緒百分之二十、網頁介面百分之十五、感測器百分之十五，以及用電子郵件通知使用者百分之五。讀一遍期末專題的架構，你可以一項不漏地把那張清單還原回來，而這是對這個設計最誠實的一句話。會議室預約面板沒有任何一個地方需要執行緒。是評分標準需要執行緒，所以計時器是多執行緒的。

那把鎖就是排程本身

閃爍是一支 pthread 程式：n 個執行緒，每個跑兩輪，每輪拿到互斥鎖、切換四顆房間 LED、睡一秒，然後釋放。鎖是跨著那個 sleep 一起持有的。先拿鎖再在裡面睡，代表任何時刻都不會有第二個執行緒進到那個迴圈裡，所以這些執行緒是嚴格一個接一個跑的，程式的行為和一個循序迴圈完全一樣。這個互斥鎖並不是在保護共用狀態不被競爭，它是被拿來當成「讓 LED 照順序閃」的那個機制。它值百分之二十，驗收也很漂亮，而它是一支畫了執行緒的循序程式。

同一個數字，三個名字

瀏覽器把計時欄位標成 Hour(s)。伺服器把同一個值放進郵件時寫成 days。然後它除以十、減一，把結果交給那支 pthread 程式，而那支程式拿它當作要建立幾個執行緒，而且是一次讀一個字元，所以兩位數的值會靜靜地掉一位。沒有人發現，因為在每一層看起來，那個數字對那一層以為的意思來說都很合理。

接線漂移了，而修正補在最上層

四顆 LED 有四個 GPIO 編號，而這些編號在每個需要它們的檔案裡都是手寫展開的。實驗二的順序是 255、481、392、254。Qt 程式的順序是 392、255、481、254。期末專題的順序是 255、392、481、254。同樣四條線，對於「哪一顆是 LED2」有三種意見。 

// lab04.js：瀏覽器的 LED1 其實是板子上的 LED3，用改名解決
let response = {
    "LED1": req.query.LED3,
    "LED2": req.query.LED1,
    "LED3": req.query.LED2,
    "LED4": req.query.LED4,
}

一張置換表，放在網頁伺服器裡，代替兩層底下那份沒被改對的接腳對照表。

這是怎麼發生的並不難想像。核取方塊在排演時點亮了錯的燈，而伺服器是當下已經開著的那個檔案，在物件裡對調三個鍵只要十秒，追接線則要二十分鐘。它可以動。但這也代表接線上的分歧還留在裡面，而且上面又疊了一個互相抵銷的錯誤，下一個要改其中任何一邊的人，會同時吃到兩個。

面板回報的是它自己的意圖

瀏覽器裡沒有任何一段程式會去問板子某個接腳現在是什麼狀態。核取方塊和圖片，都是由送出請求的那一次點擊順手設定的；Qt 版本更進一步，把那些核取方塊當成裝置狀態讀回來，於是介面同時是命令，也是這道命令的紀錄。唯一真的會讀接腳的那條路徑，是使用者空間程式裡的 state 分支，而它把答案印到標準輸出，伺服器再把它收進一個沒有人在看的 console.log。四個請求處理函式裡有三個從頭到尾不回應，所以送出請求的瀏覽器是在等一個不會來的回覆，而頁面顯示成功，是因為它根本沒有去看。

一個從來就不是設計來被自動化的介面

TX2 上的相機是用 nvgstcapture-1.0 驅動的，那是一支互動式工具：按 j 拍照、按 q 離開。它沒有「拍一張然後結束」的參數，所以伺服器把它開起來，然後對它打字。 

// final.js：自動化一支只吃鍵盤輸入的程式
const captureProcess = spawn('nvgstcapture-1.0', ['--prev-res=3']);
setTimeout(() => {
    captureProcess.stdin.write('j\n');                            // 拍照
    setTimeout(() => captureProcess.stdin.write('q\n'), 1000);    // 離開
}, 1000);

兩個 setTimeout，用來取代任何關於「那支程式準備好了沒」的知識。這是一個競爭條件，正確的做法是等它的輸出，而不是等一秒。

當時沒有人把那叫做測試，我自己也不會。但它是同一種直覺：一個為人設計的介面、一件每次都得用同樣方式發生的工作，以及一支代替手去操作控制項的程式。裡面那個時序問題就是一個 flaky test，躺在一份課程專題裡，比我有這個詞可用早了兩年。

站不住腳的地方

hazard 偵測器和驅動程式寫在上面，因為它們是重點而不是註腳。以下是其餘的部分，都是為了寫這一頁重讀儲存庫時翻出來的。這些在當年都沒有被發現，我沒有，桌邊的其他人也沒有。

七位元的運算器少了一個位元

七個一位元切片是用一個 generate 迴圈產生的，裡面有三種情況：第 0 位元、介於一和六之間的位元，以及第 6 位元。中間那個條件寫的是 (6 > i) and (i > 1)，涵蓋的是第 2 到第 5 位元。第 1 位元完全沒有被實體化，所以它的結果和進位沒有任何東西在驅動，整個字組後面的進位鏈也就斷了。驗收時在指撥開關上按出來的數字它都算對，而板子上也沒有任何東西會說出實話：顯示器上的數字看起來就是個數字。

set-on-less-than 的輸出從來沒接上任何東西

同一個實驗的一位元切片宣告了一個叫 set 的輸出，而七位元版本把最高位切片的 set 接到最低位切片的 less 輸入，那是教科書上用減法做比較的標準接法。但兩個架構都從來沒有指派過 set。兩個檔案裡那條線都在，而線上什麼都沒有。

核心模組完全相信使用者空間交給它的東西

drv_write 把 count 個位元組複製進一個固定 100 位元組的靜態緩衝區，而沒有比較這兩個數字，然後在 userChar[count - 1] 寫入結束字元，也沒有檢查 count 是不是大於零。任何打得開 /dev/demo 的行程，只要寫得夠長，就能溢位一塊核心緩衝區。read 那邊則是鏡像的問題：它只複製一個位元組卻回傳 count，等於不管實際產出多少，都告訴呼叫端「你要多少我就給了多少」。那個讀取 GPIO 的輔助函式宣告成回傳指標，而在成功的那條路徑上什麼都沒回傳。

模組是每一個請求都載入再卸載一次

每一次點擊都會跑一次 insmod、一顆一顆切換四顆 LED，再跑一次 rmmod。兩個重疊的請求會互相搶那個模組。它還會在載入時 export GPIO 接腳而從來不 unexport，所以第二次載入面對的是已經被 export 過的接腳。更糟的是包住 insmod 的那個 promise 在失敗時只印了訊息就 return，既沒有 resolve 也沒有 reject，所以載入一旦失敗，那個請求不會報錯，它只是不再存在。

一個靠提早 return 撐住的頁面

瀏覽器頁面的計時函式最後一行把一個未定義的變數指派給輸出元素，照理說每次呼叫都會拋錯。它從來沒拋，是因為一個永遠不會被填的隱藏文字輸入框，讓函式開頭的驗證檢查每次都先 return。這個頁面能動，是因為一個 bug 擋在另一個 bug 前面。另外它還有三個各自獨立的 <head> 元素，以及一個指向伺服器自己原始碼的 script 標籤，每次載入都 404，而且毫無後果。

原始碼裡的憑證

通知功能佔分數的百分之五，而我們自己的報告記載它並沒有做成功。它留下來的東西，是一個帶著學校信箱與明文密碼的郵件傳輸設定，而且不只躺在一個檔案裡，因為那段設定被複製到網頁伺服器那支程式裡又存了一份。多一份副本就是這麼一回事：錯誤變成兩倍，找到它的機會少一半。現在兩支都改讀環境變數了；而且一開始就不該用帳號本身的密碼，應用程式密碼至少可以單獨撤銷。

關鍵工程心得

  1. 要確認那個指示燈有辦法失效。hazard LED 在 demo 時亮了，於是就沒有人再往下看。它其實對作業說明書上印的那個例子永遠不會亮，而只要問一句「什麼輸入會讓這顆燈該亮卻不亮」就找得到。測到訊號會出現，不等於測到那個訊號有意義。
  2. 順序也可以是一種設計決策，而它應該被寫下來。這條管線能運作，是因為四個區塊照著某一種順序排列而不是另一種，而檔案裡沒有任何地方記載這件事。沒有人看得見的不變條件，一定會有人去破壞它。
  3. 一層的名字，不能拿來當作它在做什麼的證據。那個叫驅動程式的東西爬回 sysfs，請使用者空間的介面幫它做事。讀出一個元件實際上在做什麼、而不是它的名字承諾了什麼，就是 code review 的大半內容。
  4. 一個常數同時住在三個檔案裡，它一定會漂移，而修正一定補在錯的那個檔案。四個 LED 編號、三種順序，以及一張放在網頁伺服器裡、用來抵銷沒人去改的接線的置換表。重複本身不會造成錯誤，它決定的是錯誤會被補在哪裡。
  5. 一個只會回報自己要求了什麼的介面，不是量測儀器。兩個學期最後都留下一個由「發出命令的那段程式」自己驅動的顯示。唯一真的去讀硬體的那條路徑，把答案送進了沒有人看的日誌裡；一個系統就是這樣通過驗收，同時完全沒有告訴你它到底能不能用。
