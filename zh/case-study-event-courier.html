個人專案 · Node.js · Express · Supabase

一週寫成，事後審查

一個由在台灣的印尼裔天主教團體舉辦、約五十人參加的將臨期避靜，需要一個地方讓參加者讀到別人留給他們的鼓勵小卡，也讓任何人都能不署名地留下一張。我在活動前一週把它做出來：選自己的名字、輸入手機號碼末四碼，就能看自己的收件匣；不登入也能匿名寫給任何人。它在活動期間完成了任務。活動結束後，我用審查別人程式碼的方式重新讀了一遍，找出四個問題。這一頁談的就是這四個問題，以及修正它們花了什麼。

我的角色：唯一的開發者，期限一週，沒有人審查程式碼。這裡描述的修正都是在活動結束後、在另一個分支上完成的，每一項都有測試釘住。

  • 50 位參加者，一場活動
  • 一週內 7 次提交
  • Express 上的 6 個 API 路由
  • 審查找出 4 個問題
  • 10 個測試，不加新套件
  • 送到瀏覽器的手機號碼：0 個
隱私，以及數字的來源：這一頁不出現任何參加者的姓名、手機號碼或留言內容，畫面也只用文字描述、不附截圖。原始碼沒有附上連結：名單在活動那一週被提交進版本庫，雖然新的提交已經不再包含它，它仍留在歷史紀錄裡，所以版本庫維持私人。這裡的每一個數字都來自程式碼與它的測試。

它必須做到的事

限制來自活動本身，而不是工程。沒有人會為了一個週末的避靜註冊帳號，所以不能有註冊流程。主辦單位手上已經有報名表單整理出的名單，每位參加者一個姓名、一支手機號碼，這份名單就成了登入方式：從清單選自己的名字，再輸入號碼末四碼。留小卡則完全不需要登入，因為重點就是寄件人可以保持匿名。

伺服器是跑在 Node.js 上的 Express，提供五個頁面與六個 JSON 路由。留言存進 Supabase（託管的 PostgreSQL），因為部署的主機每次重啟都會清空磁碟，而一張隔天就消失的小卡，比沒有小卡還糟。另外寫了一支遷移腳本，先試跑、再分批把本機 JSON 紀錄裡已經寫入的留言搬進資料庫，切換之前寫下的東西一筆都沒有遺失。

有一個決定在審查時站得住：登入頁需要的參加者清單，來自一個只回傳每個人 id 與姓名的路由，所以登入時拿來比對的手機號碼，從來不會離開伺服器。

活動結束後才找到的四個問題

留言被當成 HTML 解析

收件匣用 innerHTML 組出每張小卡，把寄件人的顯示名稱和留言內容直接塞進樣板。這兩者都來自寫小卡的人，不論有沒有登入，所以一張含有標記的小卡，會在收件人的收件匣裡被當成標記解析。

實際的傷害比聽起來小，原因值得知道：伺服器會送出禁止行內腳本的 Content-Security-Policy 標頭，所以當頁面經由 Express 送出時，一張帶著 <img onerror=…> 的小卡並不會執行。但標頭只是最後一道防線，不是修正：標記仍然可以改變或偽造頁面的一部分，而在任何少了這個標頭的地方，同一張小卡就會以腳本執行，並讀到瀏覽器裡保存的工作階段權杖。

守著公開姓名的，只有四位數

登入的祕密是手機號碼末四碼：一萬種可能，而對應的姓名就列在登入頁上。嘗試次數沒有任何限制，所以一個簡短的迴圈就能把某個人的所有組合試完，讀到對方的小卡。

工作階段只存在單一執行個體的記憶體裡

登入成功後，權杖存在一個記憶體中的 Map 裡。這在一台長時間運行的伺服器上沒問題，在 serverless 主機上卻行不通：每個執行個體有各自的記憶體，一個執行個體處理的登入，下一個執行個體並不知道，而每一次冷啟動都會讓所有人登出。偏偏這個專案就附有為這類主機準備的進入點。

收件匣以姓名比對

小卡存的是收件人的姓名，而收件匣就是所有收件人姓名（轉成小寫後）與你相同的小卡。名單其實已經替每個人產生了唯一的 id，但小卡從來沒用到它，所以兩位同名的參加者，會讀到彼此的小卡。

每一項修正做了什麼

小卡與姓名現在以 textContent 放上頁面，瀏覽器只會把它們當成文字。一張含有 <img onerror=…> 的小卡，收件人現在看到的就是這串字元本身。

登入嘗試現在會被計數。同一個姓名猜錯五次就鎖定十五分鐘，即使接著輸入正確的號碼也一樣；同一個位址在同一段時間內最多嘗試二十次。被鎖定的請求會收到 429，以及說明何時可以再試的 Retry-After 標頭。

工作階段現在改成簽章，而不是儲存。權杖帶著參加者的 id 與到期時間，後面接上這兩者的 HMAC，用只有伺服器知道的密鑰計算。任何持有同一把密鑰的執行個體，都能驗證另一個執行個體發出的權杖，而聲明內容只要改一個字元，簽章就會失效。 

// Checking a token: recompute the signature, compare in constant time.
const expected = Buffer.from(this.#sign(payload));
const given = Buffer.from(signature);
if (given.length !== expected.length || !crypto.timingSafeEqual(given, expected)) {
  return null;
}

timingSafeEqual 不論簽章吻合了多少，花的時間都一樣，所以這道檢查不會透露一次猜測有多接近。

小卡現在會存收件人的 id，收件匣也改用它比對。麻煩在正式環境的資料庫：那張表沒有這個欄位，而寫入一個表裡不存在的欄位，會讓每一次新增都失敗。所以這個欄位是選擇性啟用的：在加上欄位並開啟之前，小卡的運作完全照舊；開啟之後，新的小卡依 id 送達收件人，只有改動前寫下的小卡仍以姓名比對。

名單、報名表單的回覆與留言紀錄都移出了版本控制，另附一份由虛構人物組成的範例名單供本機開發使用。在沒有磁碟的主機上，名單可以改用設定值提供，而不是檔案。

測試釘住了什麼

十個測試跑在 Node 內建的測試執行器上，沒有加入任何新套件。每個測試都在一個空閒的連接埠啟動真正的應用程式，搭配一個放著虛構名單的暫存資料夾，所以不會碰到活動的資料或資料庫。

其中三個直接檢查審查找到的問題：兩位同名的人拿到各自的收件匣；同一個姓名猜錯五次就被鎖定，之後就算輸入正確的號碼也會收到 429；一個把聲明改成別人 id、卻沿用原本簽章的權杖，會被拒絕。

有一個缺口值得說清楚：顯示方式的修正是靠讀程式碼確認的，不是靠測試。測試確認了一張小卡從伺服器回來時和送出時一模一樣；頁面接著是否把它顯示成文字，取決於只在瀏覽器裡執行的程式碼，而這套測試裡沒有瀏覽器。

它仍然做不到的事

登入與留言限制背後的計數器存在各個執行個體的記憶體裡，所以在 serverless 主機上，每個執行個體各自計數，重啟就會歸零。這讓無限制的猜測迴圈變成緩慢的迴圈；要做到共用的限制，需要資料庫裡的一張表。

登出只會在處理該請求的執行個體上撤銷權杖。在其他地方，它在到期前都仍然有效，也就是登入後十二小時。

四位數終究只是四位數。限制讓猜測變慢，卻沒有讓祕密變強。真正的修正是每位參加者一組代碼，在報名時發給本人，而這需要的是主辦單位，不是一次提交。

還有，名單仍然留在版本庫的歷史紀錄裡。新的提交已經不再包含它，但任何能讀取歷史紀錄的人都看得到，這也是原始碼維持私人、這一頁不附連結的原因。

關鍵工程收穫

  1. 截止期限過後，重新審查自己的程式碼。這裡的每一個問題，在原本的 diff 裡都看得到。活動那一週缺的不是能力，而是第二次閱讀，而最便宜的第二位讀者，就是之後的自己。
  2. 安全標頭是最後一道防線，不是修正。Content-Security-Policy 擋下了被注入的腳本，卻沒有處理腳本為什麼能被注入，而且它只保護真的帶著這個標頭的頁面。
  3. Serverless 改變了「存在記憶體裡」的意義。程序裡的一個 Map，在一台伺服器上是共用狀態，在多個執行個體上卻是各自的狀態。工作階段與流量限制都得為此重新設計，而其中只有一項能在不動資料庫的情況下修好。
  4. Schema 變更不能跟著程式碼變更一起偷渡上線。寫入正式資料表沒有的欄位，部署的那一刻就會讓每一次新增失敗。把欄位做成選擇性啟用，讓修正可以先上線，遷移等有人執行時再跟上。
  5. 執行時需要的資料，不等於需要提交的資料。名單必須放在伺服器上，卻從來不需要放進 git；而一旦放進去，刪掉檔案就不足以把它收回來。
