畢業專題 · 產學合作研究 · Sunbird Software

流程沒有問題，產出還是掉了

我們的畢業專題原本要做的，是把一個商業自動化測試團隊實際的運作方式一關一關記錄下來：從挑選需求 ticket，一路到公司自己的工程師願意合併的那個 pull request。接著我們統計了這個團隊四年的產出，發現在流程完全沒有改變的情況下，產出比高峰期掉了大約三分之二。到頭來，流程本身反而是整份研究裡最不有趣的發現。真正有趣的是：一套健康的流程，和持續下滑的數字，其實可以同時成立。

我的角色：畢業專題三位學生之一，並且在專題涵蓋的這一年半裡，以產學合作的身分實際待在團隊內部。這份報告是三個人的共同成果，指導教授為陳香君博士；報告中所記錄的實務作法，屬於公司的工程師，不屬於我們。

  • 分析 4 年的測試案例產出
  • 在團隊內部 18 個月
  • 每週投入 10–20 小時開發
  • 每兩週向公司報告一次成果
  • 從 ticket 到合併共 7 道關卡
  • 3 位學生，一位指導教授
關於保密：本文遵守我簽署的保密協議。產品名稱、內部 ticket 編號與商業邏輯均已省略或一般化，內容也未重製專題報告本身。留下來的是工程流程與數據的形狀，兩者都屬於業界通行的一般實務。

問題意識

談自動化測試最佳實務的文章從來不少，而且幾乎都是描述性的：一個有紀律的團隊會怎麼做、應該守住哪一道關卡、測試不穩定為什麼昂貴。但很少有人接著去衡量一個已經在照做的團隊，然後問一句：這些做法真的有反映在產出上嗎？

我們剛好有能回答第二個問題的位置。三個人是待在團隊裡面，而不是在外面觀察，跟著公司的工程師跑同樣的 sprint，開發的是一套企業級資料中心基礎設施管理平台。所以這份專題問的不是一個問題，而是兩個：這條流程對一個人實際上要求了什麼？以及，把幾年份的產出攤開來數，會看到什麼？

第一個問題得到的是一份描述。第二個問題得到的是一個問題，而後者更有價值，也不是我們原本預期會看到的東西。

這條流程實際要求什麼

從接下一張需求 ticket，到一個測試案例被算作完成，中間隔著七道關卡。每一道單獨看都不稀奇，真正需要紀律的是：沒有任何一道可以跳過，包括那兩道在第一次救到你之前，感覺都只是額外成本的關卡。

  1. 挑選案例在 sprint 規劃會議上從 backlog 挑出案例，並估計每一個的難度與所需工時。
  2. 先手寫測試步驟，並取得確認依需求文件細化步驟，先以手動測試找出邏輯漏洞，再把寫好的步驟送交產品經理確認。此時還沒有任何程式碼。
  3. 以關鍵字實作，而且一起寫Mob programming：整個團隊同時處理同一個案例。步驟被寫成可重用的關鍵字，遵守團隊的命名與去重複規範，完成後再跑一次 lint。
  4. 在 CI 上證明它站得住先在正常網速下跑十次，再刻意限制頻寬跑五次，讓案例必須在慢速環境下也能通過，而不只是在順暢的環境。
  5. 程式碼審查與 sprint 審查依團隊既定風格檢查程式碼，並另外向負責人展示這個 sprint 的成果。
  6. 開出 pull request分支只能透過 PR 往主線合併。
  7. 修到工程師點頭為止公司的工程師會審查並留下意見。案例不是通過測試就算完成，而是他們合併了才算完成。

第二關特別值得停下來看。用文字把測試步驟寫出來、手動跑過一遍、還要等產品經理同意，才准開始寫程式，感覺是所有起手式裡最慢的一種。但它也是唯一一道能在誤解還只是一段文字、而不是一整個測試套件的時候，就把它攔下來的關卡。

這一頁談的是流程與流程的產出。至於測試套件本身是怎麼寫成的，才能讓數百組同時跑在同一台線上伺服器上，那是另一篇案例研究。

四年的數據說了什麼

我們調出團隊連續四個年度（每年九月到隔年九月）的測試案例紀錄，統計兩個數字：建立的案例數，以及被合併的案例數。上面那條流程在這四年之間，沒有改變過。

建立的測試案例 合併的測試案例

產出在第二個年度達到高峰，約八十個案例，之後連續兩年下滑，最後掉到不足三十個。相對高峰大約掉了三分之二，最後一年甚至只比第一年剛起步時高一點。

報告把下滑歸因於三個原因，而這三個原因真正值得注意的地方，是它們的位置。需求變得更複雜，單一案例要做到完整覆蓋所需的時間因此拉長。產品版本不穩定，原本可以投入新案例的心力，改為修補被建置破壞掉的既有案例。以及跨職能團隊之間的溝通逐漸脫節，期待與需求對不起來，覆蓋範圍因此留下缺口。

沒有任何一項是「團隊變差了」。每一個原因都位在被衡量的這群人的上游，而這正是為什麼單看那個數字會產生誤導。

圖上還有一個細節支持這個讀法：最後兩個年度，合併的案例數高於建立的案例數。一個停擺的團隊不會關掉比開出更多的東西。這個形狀比較像是團隊正在消化既有的進行中工作與返工，而不是開展新的覆蓋範圍，而這恰好就是那三個原因會預期的結果。

這些數字無法斷定的事

這個發現值得說清楚，它的弱點也一樣。測試案例的數量是產出的替代指標，不是價值的指標。一個涵蓋跨子系統複雜互動的案例，和一個只涵蓋單一下拉選單的案例，同樣都算一個。如果後期的案例個別來說更難，而第一個原因正暗示如此，那麼數量的下滑就誇大了實際工作量的下滑，而我們手上沒有任何能把兩者分開的量測方式。

那三個原因是團隊自己的說法，不是實驗結果。我們沒有操作任何變因再觀察效果，而是去問了為什麼、聽了答案，並確認它和數據的形狀一致。只要標示清楚，這是可以發表的東西，但它和「已經證明」並不是同一件事。

另外，四個年度裡我們只在場於最後一年。前三年的數據是我們接手讀到的紀錄，不是我們親眼看著產生的。

必須重做一次的展示品

畢業專題理應要能展示，而我們記錄的卻是不能離開公司的工作。我們寫過的每一個測試套件、每一個關鍵字、以及它們對應的每一張 ticket，全都在保密協議之後。把真正的成果拿出來展示，從一開始就不是選項。

所以展示品是一次重建。我從零做了一個小型網頁應用程式，以及一組針對它撰寫的 Robot Framework 測試套件，刻意在一個可以公開的標的上走過同樣的七道關卡：先設計並寫下步驟、以組合而非複製的方式撰寫關鍵字、跑一次 lint、合併前重複執行。

它誠實地展示了流程，但完全沒有展示規模。真正平台的難處在於數百組套件爭用同一台線上伺服器，而一個為展示而生的小應用程式完全沒有這個問題。它忠實地模擬了流程，卻很不忠實地模擬了難題，這件事值得講明白。

主要的工程學習

  1. 流程指標不等於生產力指標。每年幾個案例，量的是做出了多少，卻完全沒有說每一個有多難。單獨拿給一個不在現場的人看，它描述的是一支正在衰退的團隊。但實際的三個原因，沒有一個在團隊的控制範圍內。
  2. 產出下滑時，要往上游看。需求複雜度成長、建置不穩定、跨團隊認知落差，這些都是從別的地方來的，最後落在守住最後一道關卡的人身上。團隊是這個數字被量到的地方，不是它被決定的地方。
  3. 最慢的那道關卡，最後是划算的。用文字寫下測試步驟、手動跑過一遍、還要等產品經理同意才能寫程式，是整條流程裡最不吸引人的一段。它也是唯一一個誤解還很便宜的地方。
  4. 「完成」是別人定義的。通過 CI 不算完成，公司的工程師核准 pull request 才算。這把「完成」的定義從作者手上移開，而它本來就不該放在那裡。
  5. 衡量自己所屬的團隊並不舒服，但仍然值得做。比較輕鬆的那個版本，是我們原本打算寫的那份描述。真正讓我們學到東西的版本，需要我們公佈一個對自己所屬群體並不好看的數字，然後謹慎地說清楚它證明了什麼、又沒有證明什麼。
