沒有重置鍵

比我的案例研究短一些的筆記，寫的是軟體測試與驗證課程的專題。我們五個人用 Appium 與 Robot Framework，替 Health2Sync 這款在我們挑上它時就已經上架的 Android 糖尿病管理 App 做自動化測試，這個 App 沒有一行是團隊寫的。沒有原始碼、沒有 API、沒有資料庫，也沒有任何測試掛鉤；想把 App 還原成原本的樣子，只能沿著 UI 把改過的每一步再點回去。

我負責的部分：設定頁這一塊，全部七個檔案。涵蓋報表匯出、單位、個人目標、日常作息與自訂食物，共十五個測試案例，以及支撐它們的頁面關鍵字庫。

  • 我負責的區塊共 15 個測試案例
  • 78 個頁面關鍵字，其中 64 個從零寫起
  • 團隊完整套件共 103 個測試案例，分布在 26 個套件裡
  • 5 個人，一個學期
  • 可用的測試掛鉤與 API 為 零
  • 1080 × 2400，手勢座標假設的螢幕尺寸

範圍與歸屬：這套測試是五個人共同完成的，我的份額大約占六分之一。這篇談的是設定頁這一塊，那七個檔案的每一行都由我提交。我那個關鍵字庫裡的 78 個關鍵字中，有 14 個沿用自隊友的版本，原始碼裡也有註解標明。我的關鍵字所依賴的共用重試機制是其他人寫的，下面談到的測試設計方法也是，那是整個團隊共同遵循的流程。 原始碼是公開的。

問題

在公司我已經很習慣透過 REST API 建立測試狀態，直接跳過介面。這裡沒有可以跳過去的介面：受測物就是手機上一個已經完成的產品。每一個前置條件都得靠點擊一步步到達，每一個斷言也都得從畫面上讀回來。

於是「狀態」就成了全部的問題。一個把血糖單位改成 mmol/L 的測試，會讓 App 就停在 mmol/L。下一個要讀血糖值的測試看到的是錯的單位，於是失敗，而且看起來像產品的缺陷。沒有重置機制，測試獨立性就不再是框架附贈的性質，而是每個測試都得自己付錢買的東西。

測試怎麼組起來

結構和我在職場上做過的關鍵字驅動測試套件一樣，只是縮小到一個人、一個功能區塊：Robot Framework 6.1.1 驅動 Appium，而一個測試案例讀起來就像一句話，裡面不會出現任何元素定位字串。

  1. 測試套件：每個設定功能一組五個檔案、十五個案例。Suite setup 負責啟動 App 並停在正確的畫面；每個案例最後都有一段 teardown，只是並非每一段都會把測試改動的東西還原。
  2. 頁面關鍵字庫：設定頁專用的 78 個關鍵字所有元素定位都只寫在這裡，所以某個畫面改版時，只需要修一個檔案。
  3. 變數檔：把測試資料命名目標範圍與作息時間都寫成具名常數，讓一個分割區間變成一個名字，而不是埋在步驟裡的一個數字。
  4. 共用底層關鍵字，由團隊撰寫包了重試機制的點擊與輸入關鍵字，會反覆輪詢直到元素出現。我的關鍵字呼叫的是這一層，而不是直接呼叫 Appium。

收尾的動作寫在 [Teardown] 裡，不論測試通過或失敗，Robot Framework 都會執行。我那十五個案例中，只有三個真的把改掉的值還原：一行把單位改回去、一個專屬關鍵字把兩個目標欄位還原成一開始的數值，還有一個把剛建立的食物刪掉。另外四個只是退出剛才進入的畫面。剩下八個按的是 App 自己的儲存鍵，其中六個等於把帳號真的改掉了：個人目標那組跑完會停在血糖目標 101 與 102，日常作息那組則會把五個時間全部留在 23:59。這是這個設計裡真正的缺口，也是我會第一個回頭修的地方。

# 改掉單位、證明它真的改了，然後再改回來。 Verify Units Of "Blood Glucose" And "Weight" Can Be Modified Click "Units" Option Modify Blood Glucose Unit mmol/L Modify Weight Unit lb Verify Blood Glucose Unit Is Changed mmol/L Verify Weight Unit Is Changed lb [Teardown] Run Keywords Modify Blood Glucose Unit mg/dL ... AND Modify Weight Unit kg

teardown 幾乎占了整個測試的一半。這就是「沒有重置鍵」要付出的代價，而這筆代價，只有那些真的把東西還原的測試付了。

看它跑起來

我那五組設定頁套件裡的四組，由 Robot Framework 驅動，直接錄自模擬器。這個專案沒有 CI，也沒有團隊以外的人看得到的報告，所以這幾段就是它最接近建置日誌的東西：App、框架，沒有人的手。畫面右緣那個小小的縮放控制項屬於模擬器，不是 App 的一部分。

這裡沒有任何一段是加速的。狀態列的時鐘照常走，所以「我的最愛食物」那個測試花在建立一筆再刪掉的十六秒，就是實實在在的十六秒。把它乘上日常作息那組要處理的五個時間選擇器，就是本頁下面那十八分鐘。每一段都只剪到 App 真正在畫面上的那一段，前後的啟動器畫面都去掉了；另外有一處是塗掉的：匯出畫面的「快速選擇」會列出一個曾經用過的信箱，那一行打上了馬賽克。

與其看中間，不如看結尾。單位那段停在 mg/dL 與 kg、目標那段停在 7,500 步與 150 分鐘、最愛食物那段停在空清單：這三個就是我十五個測試裡，真的會把改動還原回去的那三個。匯出則屬於另外四個「只退出剛才打開的畫面」的案例，而它退得起，因為它根本沒走到改動任何東西那一步。

決定要測什麼

這門課談的是測試設計而不是工具，而這也是整個專題裡，我最願意在面試中拿出來討論的部分。每一個功能在有人打開編輯器之前，都要先走過同樣的四個步驟，而被打分數的正是這四步。

  1. 先寫使用者故事用一句話寫出有人想從這個畫面得到什麼，讓測試回應的是一項需求，而不是一棵元素樹。
  2. 操作 App，把流程畫出來畫出這個 App 真正擁有的畫面與判斷分支的活動圖。因為沒有原始碼，這張圖只能從外面畫，靠實際去用它。
  3. 切開輸入空間先列出一個輸入由哪些特徵組成，再列出每個特徵可以切成哪些分割區間。一個作息時間由時與分組成；「時」有最小值、最大值，以及兩者之間的一切。
  4. 用基本選擇涵蓋它每個特徵先固定一個基準值，跑過那一列，然後每次只變動一個特徵。案例數量會隨分割區間的數量增加，而不是相乘。

用基本選擇來涵蓋輸入空間分割，是一個刻意的取捨。它假設各個特徵之間不太會互相影響，所以抓不到那種「要兩個特徵同時錯」才會出現的缺陷。團隊是明知如此才這樣選的，因為五個人用手驅動一支手機，負擔不起完整的組合。而我負責的區塊裡，唯一真的存在欄位交互作用的畫面，會在下面單獨處理。

把它套在一個真實畫面上會長成什麼樣子

團隊為「新增健康數據」畫的活動圖，直接取自我們的報告。圖上標示的每一條分支，從 TC1-1 到 TC1-7，都是一個測試案例：實際操作 App，每一個真的通往某處的判斷，就變成一個案例，末端接上它自己的輸入。我負責的區塊也長成同樣的形狀，五條分支分別帶著 2、1、6、4、2 個測試案例。這張圖畫的是另一個功能區塊，背後的程式碼是隊友寫的，但方法是我們五個人共同遵循的那一套。 開啟完整尺寸 →

這就是那套方法要求填的表格，只是換成我負責的那五個畫面。空白的格子表示這個特徵只有兩個值得分開處理的區間。表格裡的每一個值，在變數檔裡都是一個具名常數，而不是直接打在步驟裡的數字。

分割區間，取值落在它的邊緣

血糖目標要填一個下限和一個上限。我的套件涵蓋這組數對的五個分割區間：三組有效範圍，接著是兩端相等，以及下限大於上限。三組有效數對分別是 99 與 100、98 與 99、101 與 102，而且每一組都會被寫進畫面上的三個目標裡，也就是餐前、餐後與睡前。每一組有效數對都只差一，這讓無效的那兩個區間，也就是 100 與 100 以及 101 與 100，都剛好只離合法值一步。只要規則差了一，就會被只差一的數字抓出來。

無效案例要驗證的是「被拒絕」這件事

「拒絕錯誤輸入」本身就是一項功能，所以那些無效案例不會只寫成「然後什麼事都沒發生」。它們會斷言 App 實際跳出的警告文字，也就是上限必須高於下限，接著再把對話框關掉。如果 App 只是默默沒存檔，比較寬鬆的測試會放它過關，但這些案例會失敗。

跨越多個欄位的限制條件

日常作息是一天當中的五個時間點，彼此必須維持先後順序，所以午餐一定要落在早餐和晚餐之間。沒有任何單一欄位能驗證這件事，而這也正是基本選擇註定會漏掉的東西：這個準則每次只變動一個特徵，但這條規則要兩個欄位互相牴觸才會被打破。所以那四個案例裡有三個，是把時間這個特徵掃過它的各個分割區間，把 00:00、12:30 與 23:59 分別寫進五個作息裡，再逐一確認讀回來的值正確。第四個則反過來設計：先把早餐推到午餐之後，斷言 App 跳出的那句抱怨，關掉對話框，接著再把晚餐推到睡前時間之後，連第二句抱怨也一併斷言。一個測試，兩種打破順序的方式。

那一個測試的活動圖。圖上那兩個判斷點就是它存在的全部理由，也正是任何「一個欄位一組分割」都到不了的地方。

前置條件用寫的，不用猜的

報表匯出那組測試，只有在測試本身無法製造的條件下才會通過：免費帳號只能匯出三次，而且所選的期間內必須要有資料。與其讓這件事日後被誤認成測試不穩定，套件直接把它寫在檔案開頭。一個誠實的前置條件，價值遠高於一個每季莫名其妙失敗一次的測試。

它做不到的事

少了這一節，這篇筆記就不誠實了；何況原始碼本來就是公開的。

有五個關鍵字被綁死在單一螢幕尺寸上

「捲到頁面底部」和「把時間滑桿往前後各推一小時」，都是在寫死的像素座標之間滑動完成的，而那些座標是在 1080 乘 2400 的螢幕上量出來的；我從隊友那裡沿用過來的兩個數字選擇器滑動也一樣。換到任何其他裝置，它們就會滑到別的地方。我在自己那幾個上面把解析度寫成註解，這只是把問題記錄下來，並沒有解決它。

靠 UI 收尾，可靠度就只等於 UI 的可靠度

靠一路點回去的 teardown，前提是 App 停在 teardown 預期的位置。如果測試是在某個對話框中途失敗的，teardown 就會從錯誤的畫面開始，留下的爛攤子則由下一個執行的測試承接。真正能解決這件事的只有一個真正的重置介面，沒有別的辦法。

四個測試案例，跑掉十八分鐘

日常作息那組套件，在我們交出去的那次執行裡花了 1,089 秒。四個測試案例、十八分鐘，而且幾乎全部耗在介面上：五個時間選擇器被滑到定位、讀回來，離開前再被滑一次。這裡沒有任何東西是平行跑的，而慢成這樣的套件，是不會有人坐在那裡等它跑完的。

沒有任何東西會自己跑

沒有 CI、沒有排程執行，除了 Robot Framework 在本機產出的報表之外也沒有任何回報機制。沒有人在跑的測試套件其實是文件，而這一套目前比較接近文件，而不是一張安全網。

我從中學到的事

  1. 測試獨立性是買來的，不是天生就有的。有 API 可以建立狀態時，我從來不需要想「誰負責收尾」。沒有 API 的時候，收尾就變成每一個測試都要做的設計決策，而且它會是最先壞掉的東西。
  2. 替分割區間命名，就完成了大半的工作。一個叫做 BLOOD_GLUCOSE_GOAL_LOW_HIGHER_THAN_HIGH 的常數，會直接告訴下一個讀到它的人這個案例在測什麼；直接寫在步驟裡的兩個數字永遠做不到這件事。
  3. 把測試對外界的要求寫下來。匯出次數的限制遲早會咬到某個人。在套件開頭寫上一句話，就能把一次未來的神祕失敗，變成一項已知的限制。
