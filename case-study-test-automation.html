How 730+ Tests Run at Once Without Stepping on Each Other

Writing one browser test is easy. Writing the two-thousandth one is a different problem entirely: it has to run at the same time as hundreds of others, against a single live server, and still tell you the truth in the morning. This is what I learned working inside that problem during my co-op and internship at Sunbird Software, on the quality platform for an enterprise data-center infrastructure management (DCIM) application.

My role: turning ticket-level requirement specifications into automated end-to-end suites that cleared the platform's merge gate. The platform itself is the team's work. This case study is about what building inside it taught me.

  • 730+ executable end-to-end suites
  • Thousands of test cases and reusable keywords
  • 100% pass threshold in CI
  • Overnight parallel regression runs
  • Zero lint warnings allowed to merge
  • 10 consecutive green runs to merge
A note on confidentiality: this write-up respects my NDA. Product and client names, internal identifiers, and business logic are omitted or generalized; everything here describes industry-standard engineering practice. Scale figures describe the team-owned platform I worked in daily, and my personal contributions are called out explicitly.

The Problem

A mature enterprise web platform ships releases continuously, and every feature (asset management, capacity planning, connectivity, data import/export) interacts with the others through one live, stateful server. Manual regression at that scale is impossible, and naive UI automation fails in two predictable ways: tests that are flaky (timing races, stale DOM elements, browser quirks) and tests that are unsafe in parallel (two suites mutating the same shared subsystem at once).

The engineering challenge is not writing Selenium scripts. It is keeping thousands of UI test cases trustworthy enough that a 100% pass threshold is realistic, fast enough to fit a fixed nightly budget, and safe enough that dozens of suites can run at once against one server.

The Technical Solution

The platform is a layered, keyword-driven architecture on Robot Framework and Selenium, executed in parallel by Pabot under Jenkins. My day-to-day work was acceptance-test-driven. Each ticket-level requirement specification became an automated suite, composed from a shared domain keyword library and provisioning its test state through a REST API facade instead of slow UI flows. Then it had to survive the merge gate: static analysis with custom lint rules, ten consecutive green runs, and five further passes under simulated slow-network throttling.

The steps came before the code. Each case was first written out as plain-text test steps, walked through by hand against the product, and confirmed with the product manager, so the automation encoded a procedure that was already known to be right. Implementation often ran as mob programming, the whole team at one screen taking turns at the keyboard, which is how coding conventions actually spread through a team faster than a style guide can.

Architecture & Approach

Parallelism with explicit resource semantics

Hundreds of suites share one live server, so the platform uses a tag-based distributed lock manager built on Pabot's shared-memory library: a suite that touches a shared subsystem (say, file import) declares it with a tag, and a listener serializes only the suites that genuinely conflict. Locks are acquired at suite level as a whole to prevent deadlock, and every lock transition is exported in a standard trace format so parallelism can be inspected visually. Writing new tests meant understanding this contract and declaring the right resources, so my suites were parallel-safe by construction.

Flakiness treated as an engineering problem

Instead of sprinkling sleeps into tests, the platform centralizes stability in a listener pipeline applied to every run: a fixed pacing delay after each interaction so the browser is never rushed past what a real user would do, patched waits that tolerate stale DOM elements, a retry for a known browser interaction race, guaranteed browser teardown, and password redaction before anything reaches the logs. When a test fails, browser console and network logs are attached to the report, for failing tests only, so a red result arrives with its own forensics.

Quality gates for the tests themselves

Test code is held to production standards. Every new suite passes a custom static analysis ruleset with zero warnings, runs green ten times consecutively, then five more times under network throttling before merge. In CI, results below 100% pass mark the build. The gate is what makes a suite this size trustworthy: nobody debates whether a red build is "probably just flaky."

Beyond functional tests

Functional testing was only one lane. The same platform carries API performance testing, with CSV-parameterized load profiles and concurrency sweeps tuned so results stay comparable between levels, and a Python pipeline that turns raw output into formatted summaries on its own. I did not build that side, but working next to it is where I learned what a performance regression actually looks like in a number, and how much unglamorous automation sits behind a release nobody has to babysit.

Key Engineering Learnings

  1. Test code is production code. Linting with custom rules, review checklists, and even unit tests for the test infrastructure itself. Rigor applied to tests is what makes their verdicts meaningful.
  2. Flakiness is a solvable problem, not weather. Every "random" failure has a mechanism, whether timing, staleness, or a browser race, and centralizing the countermeasures in shared infrastructure fixes it once for thousands of tests.
  3. Parallelism needs explicit contracts. Concurrent tests against shared state only work when dependencies are declared, not assumed. A few tags per suite, and everything that doesn't conflict runs at the same time.
  4. Fast feedback is designed, not hoped for. API-based setup instead of UI flows, front-loading slow suites in the scheduler, and a small PR smoke subset are deliberate design choices that keep iteration fast.
  5. Observability turns debugging into data. Trace-event exports, failure-only diagnostics, and per-suite timing logs replace guesswork with evidence, for the test platform just as much as for the product.
