案例研究 · 測試自動化 · Sunbird Software

730+ 項測試如何同時執行而互不干擾

寫一支瀏覽器測試很簡單，寫到第兩千支就完全是另一回事：它得和其他數百支測試同時執行，對著同一台運作中的伺服器操作，隔天早上還要給你可信的答案。這篇談的是我在 Sunbird Software 產學合作與實習期間，投入這個問題所學到的東西，當時負責的是一套企業級資料中心基礎設施管理（DCIM）應用程式的品質平台。

我的角色：把工單層級的需求規格轉成能通過平台合併關卡的自動化端對端測試套件。平台本身是團隊的成果，這篇案例研究寫的是我在裡面開發所學到的事。

  • 730+ 組可執行的端對端測試套件
  • 數千個測試案例與可重複使用的關鍵字
  • CI 中 100% 的通過門檻
  • 整夜平行執行的迴歸測試
  • 合併前 lint 警告必須為 零
  • 合併前需連續 10 次執行全綠

關於保密：本文遵守我簽署的保密協議（NDA）。產品與客戶名稱、內部識別碼與商業邏輯皆已省略或一般化，文中所述全部都是業界通用的工程作法。規模數字描述的是我每天實際參與、由團隊共同擁有的平台，我個人的貢獻則會明確標示出來。

問題

一套成熟的企業級 web 平台會持續發布版本，而每項功能（資產管理、容量規劃、連線管理、資料匯入匯出）都透過同一台具狀態且運作中的伺服器彼此互動。這種規模不可能靠人工做迴歸測試，而天真的 UI 自動化會以兩種可預期的方式失敗：測試 不穩定（時序競爭、DOM 元素失效、瀏覽器怪癖），以及測試 無法安全平行執行（兩組套件同時改動同一個共用子系統）。

所以真正的工程難題不是「寫 Selenium 腳本」，而是：要怎麼讓數千個 UI 測試案例可信到讓 100% 通過門檻成為合理要求、快到能塞進每晚固定的時間預算，又安全到可以讓數十組套件同時對著一台伺服器執行？

技術解法

平台的答案是一套建立在 Robot Framework 與 Selenium 之上、分層且以關鍵字驅動的架構，並在 Jenkins 上由 Pabot 平行執行。我日常的工作以驗收測試為導向：每一份工單層級的需求規格都會變成一組自動化套件，內容全部由共用的領域關鍵字庫組合而成，測試狀態透過 REST API 外觀層建立，而不是走緩慢的 UI 流程；接著還得通過合併關卡，包括採用自訂 lint 規則的靜態分析、連續十次全綠的執行，以及在模擬慢速網路節流的情況下再通過五次。

程式碼之前，先有步驟。每個案例都會先用純文字把測試步驟寫出來、以手動方式對著產品實際走一遍，再經產品經理確認，所以自動化編寫的是一套已經被驗證過的流程。實作時常以 mob programming 進行，全隊圍著同一個畫面輪流敲鍵盤；比起任何風格指南，這才是讓程式撰寫慣例真正在團隊裡傳開的方式。

  1. 測試套件：每張需求工單一組好讀、以規格驅動的情境，完全由共用關鍵字組合而成
  2. 領域關鍵字庫：數千個可重複使用的關鍵字各功能領域的可重用步驟 · 自訂的 Selenium 擴充 · 用於快速建立與清理環境的 REST API 外觀層
  3. 監聽器管線：橫切關注點日誌中的機密遮罩 · 貼近真人反應時間的節奏控制 · 容忍失效元素 · 針對性重試 · 僅在失敗時擷取網路與主控台記錄
  4. 平行排程器：Pabot 加上分散式資源鎖測試以標籤宣告會用到的共用子系統，會衝突的套件改為循序執行，其餘全部同時進行
  5. CI 調度：Jenkins自動還原資料庫與建置環境 · 快速的 PR 冒煙測試子集，對比整夜的完整執行 · 以 JaCoCo 量測後端覆蓋率

架構與作法

以明確的資源語意支撐平行執行

數百組套件共用同一台運作中的伺服器，因此平台以 Pabot 的共享記憶體函式庫為基礎，做了一套以標籤為依據的分散式鎖管理器：只要套件會動到共用子系統（例如檔案匯入），就用標籤宣告出來，再由監聽器只把真正會衝突的套件排成循序執行。鎖一律以整組套件為單位取得，避免死結；每一次鎖的狀態轉換都會以標準的 trace 格式輸出，讓平行狀況可以用視覺化的方式檢視。寫新測試代表要理解這份約定並宣告正確的資源，所以我寫的套件在結構上天生就能安全平行執行。

把測試不穩定當成工程問題來解

平台不是在測試裡到處灑 sleep，而是把穩定性集中在每次執行都會套用的監聽器管線裡：每個互動之後固定延遲一小段時間，讓瀏覽器不會被推得比真實使用者還快；修補過的等待機制可以容忍失效的 DOM 元素；針對已知的瀏覽器互動競爭狀況做重試；確保瀏覽器一定會關閉；以及在任何內容寫進日誌之前先遮蔽密碼。測試失敗時，瀏覽器主控台與網路記錄會附在報告上，而且只針對失敗的測試，讓每個紅燈結果都自帶足以追查原因的證據。

針對測試本身的品質關卡

測試程式碼比照正式產品的標準要求。每一組新套件都要在自訂的靜態分析規則下零警告通過、連續十次執行全綠，接著在網路節流的情況下再通過五次，才能合併。在 CI 中，通過率未達 100% 的結果會讓該次建置被標記為失敗。正是這道關卡讓這種規模的測試套件值得信任：沒有人需要爭論紅色的建置是不是「大概只是測試不穩定而已」。

功能測試之外

功能測試只是其中一條線。同一個平台上還有 API 效能測試：以 CSV 參數化的負載設定，在一系列虛擬使用者數量之間做並行度掃描，並調整負載設定讓不同層級的結果保持可比較，另外有一條 Python 流程會自動把原始結果收斂成格式化的摘要報表。這部分不是我做的，但在旁邊一起工作，讓我實際看懂效能退化在數字上長什麼樣子，也看到一次不需要有人盯著的發版背後，累積了多少一點也不華麗的自動化。

主要工程收穫

  1. 測試程式碼就是正式程式碼。用自訂規則做 lint、審查用的檢查清單，甚至為測試基礎設施本身寫單元測試。對測試投入的嚴謹，正是讓測試結果具有意義的原因。
  2. 測試不穩定是可以解決的問題，不是像天氣一樣只能認命。每一次「隨機」失敗背後都有機制，可能是時序、元素失效或瀏覽器的競爭狀況，而把對策集中在共用的基礎設施裡，修一次就等於替數千個測試修好了。
  3. 平行執行需要明確的約定。針對共用狀態同時執行的測試，只有在相依關係被明確宣告而不是靠假設時才行得通。每組套件加上幾個標籤，所有不衝突的部分就能同時執行。
  4. 快速回饋是設計出來的，不是期待出來的。用 API 建立測試前置狀態而不是走 UI 流程、在排程中把慢的套件排在前面，以及只跑一小組 PR 冒煙測試，都是刻意的設計選擇，為的是讓迭代維持快速。
  5. 可觀測性讓除錯變成看資料。trace 事件輸出、只在失敗時產生的診斷資訊，以及每組套件的耗時記錄，都用證據取代猜測，對測試平台和對產品同樣適用。
