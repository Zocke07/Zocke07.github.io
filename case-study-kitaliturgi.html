Self-Directed Project · JavaScript · Date Arithmetic

Count Backwards From the Fixed Point

KITA Liturgi is a guide for the altar servers and lectors of an Indonesian Catholic community in Taiwan. Most of it is static: procedures for each role, patron saints, a copy of the missal's general instruction. One page is not. It has to answer, for whatever day you happen to open it, which Sunday of the liturgical year this is, which season, which liturgical color, and which of the three reading cycles is running. There is no data file behind that page and no API call. Every answer is derived from a single computed date, and for eight months the derivation was wrong on two thirds of the Sundays it was asked about.

My role: self-directed, for a ministry group that uses the site in practice. No team, no reviewer, and no test suite to catch me, which is the part worth being honest about: a week number is output that nobody can check by eye. "Twenty-second Sunday in Ordinary Time" reads exactly as plausible as the twenty-third, so a wrong answer looks identical to a right one until you go and derive it independently.

  • 10 pages, static, no build step
  • 544 lines of calendar logic
  • 0 external calendar data sources
  • 154 Sundays audited after Pentecost
  • 102 of them named wrongly
  • 15 years re-verified, 2026 to 2040
Scope, and where the numbers come from: this is a static site of hand written HTML, CSS and three JavaScript files, deployed on Vercel. The counts on this page were not read off a commit message. I loaded the pre-fix and post-fix modules side by side in Node with a stubbed DOM, ran both over every Sunday from 2026 to 2040, and diffed the output; the audit script and its numbers are quoted below as they printed. The site is live and the repository is public. Both are in Indonesian, which is the language its readers use. Code comments and the season names printed in the audit's output are translated to English for readability. Source code quoted verbatim, including the string literals inside it, is not: it reads exactly as the linked file does, "Minggu Biasa" included.

What the Page Has to Answer

Open the calendar page and it tells you four things about the coming Sunday: its proper name, the season it falls in, the liturgical color, and the year of the three-year reading cycle. The site theme repaints itself to match that color, so violet in Advent and Lent, green through Ordinary Time, white at Christmas and Easter, red at Pentecost. That last part is why a wrong answer is not cosmetic. It changes what the page tells a nineteen-year-old lector to wear and to expect.

None of this is looked up. There is no calendar JSON in the repository and nothing is fetched at runtime. The whole module is a derivation from one number, the year, and the reason it can be is that the Western liturgical calendar has exactly two kinds of date in it. Anchored dates never move: Christmas is 25 December, the Epiphany is 6 January. Movable dates all hang off Easter, which is itself computed.

The computus, unchanged since the first commit and the one part that was never wrong.

function calculateEaster(year) {
    const a = year % 19;
    const b = Math.floor(year / 100);
    const c = year % 100;
    // ... Meeus/Jones/Butcher, twelve more lines of integer arithmetic
    const month = Math.floor((h + l - 7 * m + 114) / 31);
    const day = ((h + l - 7 * m + 114) % 31) + 1;
    return new Date(year, month - 1, day);
}

Everything movable is then an offset from that return value. Ash Wednesday is Easter minus 46 days, Palm Sunday is Easter minus 7, Pentecost is Easter plus 49. Advent is anchored instead, four Sundays before Christmas, and Christ the King is the Sunday before Advent begins. Two independent anchors, one at each end of the year, with a movable feast sliding around in between them. That geometry is the whole story.

Ordinary Time Is Not One Stretch

Ordinary Time is the green season, and it is numbered: the Second Sunday in Ordinary Time, the Third, and so on. What makes it awkward to compute is that it does not run continuously. It starts after the Baptism of the Lord in January, stops dead at Ash Wednesday, and does not resume until the Monday after Pentecost, by which point three months have gone by. The numbering, however, carries straight across the gap as though nothing had happened.

So the obvious implementation is to count Sundays from the start and keep counting. That is what I wrote. It is wrong, and the diagram is the quickest way to see why.

Why Counting Forward Cannot Work

The original code did something slightly cleverer than counting calendar weeks, which is what made it survive review by me. It counted the Ordinary Time Sundays before Lent, then counted the Sundays since Pentecost, and added the two together.

The old resume, from the first commit. It reads as though it must be right.

// Ordinary Time: split before Lent and after Pentecost
const weeksBeforeLent = Math.floor((sundayBeforeAshWed - startOrdinary) / msWeek) + 1;
const weekAfterPentecost = Math.floor((sundayDate - firstSundayAfterPentecost) / msWeek) + 1;
const weekNumber = weeksBeforeLent + weekAfterPentecost + 1;

The assumption buried in that last line is that the two stretches, laid end to end, add up to the year. They do not, and the reason is that Ordinary Time is defined to be 34 weeks long, always, while the calendar year it has to fit inside is not a constant number of Sundays. Some years there is room for all 34 and some years there is not. When there is not, the church does not renumber the end of the year; it drops a week at the resume, so that Christ the King still lands on the thirty-fourth Sunday.

That is the fact the addition cannot represent. Counting forward from the start knows how many Sundays have gone by, but it has no way of knowing how many are left, and the dropped week is decided by what is left. In the diagram the two green stretches are different lengths in the two years, and yet both finish on 34. The count is pinned at the far end.

102 of 154

Before changing anything I wanted to know how bad it was, which meant running both versions rather than reasoning about them. Loading a browser module in Node needs a stubbed document, and after that the two implementations can be called side by side over any range of dates.

The audit, over the six years a visitor might plausibly look at. The function returns Indonesian, "Minggu Biasa" for Ordinary Time; translated below so the transcript reads without it.

$ node verify.js
Post-Pentecost Ordinary Time Sundays 2026-2031: 102 of 154 differ

$ node verify.js --sample
2026-05-30  old=Ordinary Time 8   new=Ordinary Time 9
2026-06-06  old=Ordinary Time 9   new=Ordinary Time 10
2026-06-13  old=Ordinary Time 10  new=Ordinary Time 11
2026-09-06  old=Ordinary Time 22  new=Ordinary Time 23

Two thirds of them, and the errors are not scattered noise. Once a year drifts it stays drifted for the rest of that year, so a reader who checked in September was being given a number that had been wrong every single week since May. The last line is the one that started this: 6 September 2026 is the Twenty-third Sunday in Ordinary Time, and the home page was calling it the Twenty-second.

The years that came out right were right by luck. 2035 happens to be a year where the arithmetic and the rule agree, which is exactly the kind of coincidence that keeps a bug alive: spot-check the wrong year and the implementation looks fine.

Anchor the Count at the End

Christ the King is not a movable feast in the way Easter is. It is defined as the last Sunday before Advent, Advent is defined as four Sundays before Christmas, and Christmas does not move. So its position is known without reference to Easter at all, and by definition it is the thirty-fourth Sunday in Ordinary Time. That is a fixed point, and a fixed point is the thing a count wants to be tied to.

The replacement. One line, and it never needs to know what happened earlier in the year. Quoted verbatim, so the string it builds is still "Minggu Biasa", Indonesian for Ordinary Time.

// Ordinary Time after Pentecost: Lent and Easter consume a variable number of
// weeks, so counting forward is guaranteed to drift. Christ the King is always
// the 34th Sunday in Ordinary Time, so count backwards from there.
if (day > pentecost && day < adventStart) {
    return `Minggu Biasa ${34 - weeksBetween(day, getChristTheKing(year))}`;
}

The subtraction replaces the addition and the intermediate quantities disappear with it. weeksBeforeLent is not computed any more, because the answer no longer depends on it. That is usually the sign that a fix is the right shape rather than a patch: the corrected version has fewer moving parts than the broken one, not more.

weeksBetween rounds rather than truncating, which matters more than it looks. The visitor's clock is doing this arithmetic in local time, and across a daylight saving boundary two dates that are 21 days apart are 20 days and 23 hours apart in milliseconds. Truncating turns that into two weeks and loses a Sunday. Taiwan and Indonesia, where the readers are, do not observe daylight saving, so this would never have shown up in testing where the site is used.

Verification is the anchor itself: for every year from 2026 to 2040, compute Christ the King independently and ask the function what it calls that date. Fifteen years, fifteen times week 34.

Four More in the Same Function

Auditing one branch meant reading all of them, and the neighbors did not survive the reading. None of these are subtle. They are the kind of thing that stays in a file because nobody ever looks at the file again after it appears to work.

  1. The Christmas branch could never match. It tested whether a December date fell before the Baptism of the Lord, but computed the Baptism for the same calendar year, which is the previous January. Every December Sunday failed a test that was structurally impossible to pass.
  2. Pentecost was labeled the eighth Sunday of Easter. The Easter season has seven Sundays; Pentecost closes it and has its own name. The range check ran to <= pentecost and let it fall through.
  3. Palm Sunday compared timestamps. It used getTime() equality against a date constructed at midnight, so any date carrying a time of day, which is every date derived from new Date(), missed by however many hours had passed that day.
  4. The first Sunday of the year was "Ordinary Time 0". A Sunday landing before Ordinary Time had started produced a zero, printed to the page as a season nobody has ever celebrated.

There was also a disagreement between two functions that had each been written to be correct on its own. getLiturgicalSeason used a fixed 6 January Epiphany, while the feast list used the transferred Sunday date that most dioceses actually observe. Those two rules agree in most years and disagree in 2029, so the season banner and the feast list would have contradicted each other on the same page, in one year, four years out. Both call the same helper now.

What Else the Same Reading Turned Up

The calendar was the reason to open the repository, but reading it properly for the first time in eight months turned up a good deal that had nothing to do with dates.

The home page shipped about 38 MB. The gallery was serving full-resolution originals straight off a DSLR, up to 6000 by 4000 pixels and 7.6 MB each, displayed as 250-pixel-tall thumbnails, and they were the only images on the site without loading="lazy". Resizing each image to the size it is actually displayed at, adding the lazy attribute and width and height so the browser can reserve space, then converting everything to WebP and dropping a 106 KB icon webfont that existed to draw one Instagram glyph, took arrival weight to 510 KB and a full scroll to 957 KB.

Nine of the ten pages threw on every scroll event. The scroll handler dereferenced the back-to-top button unconditionally, and that element only exists on the home page. The navigation submenu was hover-only, so on a phone the procedure pages could not be reached from the nav at all, which is most of the audience. The hamburger was a <div>, unreachable by keyboard, and the closed mobile menu stayed in the focus order while off-screen. The scroll spy compared a bare fragment against a full path, so it removed the active class and never put it back.

The theme flashed violet. The default colors in :root are the violet of Advent, and the real liturgical color was applied on DOMContentLoaded, so every visitor saw a violet frame before the page repainted to whatever the season actually was. Loading the calendar module in the head and calling the theme function during parse puts the right color on the first frame.

What It Still Does Not Do

The calendar computes the temporal cycle, which is the seasons and the Sundays. It does not implement the sanctoral cycle, so a saint's day that outranks a Sunday will not displace it, and it does not know the Indonesian national calendar, where some solemnities are transferred to the nearest Sunday by the local bishops' conference. For the four things the page claims to tell you, this is correct; anyone wanting a full ordo is pointed at one, which is why the page links out to GCatholic rather than pretending to replace it.

There are still no tests in the repository. The verification described here was a throwaway Node script that loaded two revisions side by side, and it lives in my shell history rather than in the project. Committing it as a test would have been the right move and I did not do it, which means the next person to touch this function, including me, gets exactly the same lack of a safety net that let the original bug through.

The WebP conversion has no JPEG fallback, so the images need Safari 14 or newer, from 2020. Two role-card photographs are also still missing from the repository and fall back to stock images from Unsplash through an onerror handler, which is a placeholder that has outstayed its welcome.

Key Engineering Learnings

  1. Anchor a count to whichever end is fixed. Ordinary Time has a variable start and a defined end, so every count in it should run backwards from the end. The forward version needed two intermediate quantities and got the answer wrong; the backward version needs none and cannot.
  2. Plausible output is the hardest kind to check. A crash announces itself and a blank page announces itself. "Twenty-second Sunday in Ordinary Time" announces nothing, and it sat on the front page for eight months. Output that a reader cannot validate by eye is exactly the output that needs a test, and it is the output least likely to get one.
  3. Spot-checking a rule confirms the year you picked, not the rule. 2035 gives the same answer either way. Had I checked that year I would have closed the tab satisfied. The audit only meant anything because it ran every Sunday in a fifteen-year range rather than the one I would have chosen.
  4. Two correct functions can still contradict each other. The fixed Epiphany and the transferred Epiphany are both defensible readings, and each function was right by its own. It is the disagreement between them, surfacing on one page in 2029, that was the defect. Shared rules belong in one helper, even when duplicating them looks harmless.
  5. Reading your own old code is a distinct activity from writing it. The scroll handler that threw on nine pages, the hover-only menu that shut out every phone, and the violet flash on first paint had all been shipped and lived with. None of them needed skill to find. They needed somebody to sit down and actually read the file, which is not the same as having written it.
