Project Notes · Mobile Test Automation · Course Project

No Reset Button

Shorter notes than my case studies, on the project for a software testing and verification course. Five of us automated Health2Sync, a diabetes management app that was already shipping when we picked it, with Appium and Robot Framework. Nobody on the team wrote a line of it. No source code, no API, no database, no test hooks, and no way to put the app back the way we found it except by driving the UI back through every change we made.

My part: the settings area, all seven of its files. Fifteen test cases across report export, units, personal goals, daily routines, and custom foods, plus the page keyword library underneath them.

  • 15 test cases in my area
  • 78 page keywords, 64 written from scratch
  • 103 test cases across 26 suites, team-wide
  • 5 people, one semester
  • Zero test hooks or APIs available
  • 1080 × 2400, the screen the gestures assume

Scope and credit: the suite is a five-person team effort and my share of it is about a sixth. What I claim here is the settings area, where I committed every line of all seven files. Fourteen of the 78 keywords in my library are reused from a teammate's, marked as such by a comment in the source. The shared retry primitives my keywords are built on were written by others, and so was the test design method below, which the whole team worked to. The repository is public.

The Problem

At work I had gotten used to setting up test state through a REST API and skipping the interface entirely. Here there was no interface to skip to. The app under test was a finished product on a phone. Every precondition had to be reached by tapping, and every assertion had to be read off the screen.

That makes state the whole problem. A test that changes the blood glucose unit to mmol/L leaves the app in mmol/L. The next test to read a glucose value sees the wrong one, fails, and looks like a product bug. With no reset, test independence stops being a property of the framework and becomes something each test has to pay for itself.

How the Tests Are Built

Same shape as the keyword-driven suites I worked on professionally, scaled down to one person and one feature area: Robot Framework 6.1.1 driving Appium, and a test case that reads as a sentence and holds no locators.

  1. Test suites: one per settings featureFive files, fifteen cases. Suite setup launches the app and lands on the right screen; every case ends with a teardown, though not every teardown restores what the test changed.
  2. Page keyword library: 78 keywords for the settings areaEvery locator lives here and nowhere else, so a screen that gets redesigned is one file to fix.
  3. Variables file: the test data, namedGoal ranges and routine times as named constants, so a partition is a name rather than a number buried in a step.
  4. Shared primitives, written by the teamRetry-wrapped click and input keywords that poll until the element appears. My keywords call these rather than raw Appium.

The cleanup runs in [Teardown], which Robot Framework runs whether the test passed or failed. Three of my fifteen restore the value they changed: one line to put a unit back, a keyword of its own to return two goal fields to where they started, and one that deletes the food it created. Four more only navigate out of the screen they opened. The remaining eight press the app's own save button, and six of those leave the account genuinely modified, the goals suite ending with blood glucose targets at 101 and 102 and the routines suite with all five times at 23:59. That is the real gap in this design and the first thing I would fix.

# Change the units, prove they changed, then change them back. Verify Units Of "Blood Glucose" And "Weight" Can Be Modified Click "Units" Option Modify Blood Glucose Unit mmol/L Modify Weight Unit lb Verify Blood Glucose Unit Is Changed mmol/L Verify Weight Unit Is Changed lb [Teardown] Run Keywords Modify Blood Glucose Unit mg/dL ... AND Modify Weight Unit kg

The teardown is half the test. That is what no reset button costs you, and it is a cost only the tests that actually restore something have paid.

Choosing What to Test

The course was about test design rather than tooling, and this is the part of the project I would defend in an interview. Every feature went through the same four steps before anyone opened an editor, and those steps are what was actually graded.

  1. Write the user storyOne sentence about what somebody wants from the screen, so the tests answer a need rather than an element tree.
  2. Walk the app and draw the flowAn activity diagram of the screens and decisions the app really has. With no source code, the diagram gets drawn from the outside, by using the thing.
  3. Split the input spaceList what an input is made of, then the blocks each part breaks into. A routine time is an hour and a minute; an hour has a minimum, a maximum, and everything between.
  4. Cover it with base choiceFix one base value per characteristic, run that row, then vary one characteristic at a time. The case count grows with the number of blocks instead of multiplying.

Input space partitioning covered by base choice is a deliberate trade. It assumes the characteristics do not interact much, so it will not find a bug that needs two of them wrong at the same time. The team took that trade on purpose, because five people driving one phone by hand cannot afford the full combinations. The one screen in my area where fields genuinely do interact is handled further down.

Blocks, and values taken from the edge of them

The blood glucose goal takes a low and a high. My suite covers five blocks of that pair: three valid ranges, then the two ends equal, then the low above the high. The valid pairs are 99 and 100, 98 and 99, and 101 and 102, and each is written into all three goals the screen carries, before meal, after meal, and bedtime. Every valid pair is one apart, which puts the invalid blocks, 100 and 100 and then 101 and 100, exactly one step from something legal. A rule that is off by one gets caught by numbers that are one apart.

The invalid cases assert on the refusal

Rejecting bad input is a feature, so the invalid cases are not written as "and nothing happens". They assert the exact warning text the app shows, that the high end should be higher than the low end, and then dismiss it. A silent failure to save would pass a weaker test and fails these.

Constraints that span more than one field

Daily routines are five times of day that have to stay in order, so lunch must fall between breakfast and dinner. No single field can validate that, and it is exactly what base choice is built to miss: the criterion varies one characteristic at a time, and this rule only breaks when two fields are set against each other. So three of the four cases sweep the time characteristic through its blocks, 00:00, 12:30 and 23:59 written into all five routines, and check each one reads back correctly. The fourth is built the other way round. It pushes breakfast past lunch, asserts the complaint the app makes, closes the dialog, then pushes dinner past bedtime and asserts that second complaint too. One test, two ways to break the ordering.

Preconditions written down instead of assumed

The report export tests only pass under conditions the test cannot create: a free account has three exports, and there has to be data in the period selected. Rather than let that look like flakiness later, the suite documents it at the top. An honest precondition is worth more than a test that fails mysteriously once a quarter.

What It Cannot Do

These notes would be dishonest without this section, and the repository is public anyway.

Five keywords are pinned to one screen size

Scrolling to the bottom of a page, and nudging a time slider an hour in either direction, are done by swiping between hard-coded pixel coordinates measured on a 1080 by 2400 screen. The two number-picker swipes I inherited from a teammate do the same. On any other device they land somewhere else. I wrote the resolution into a comment above mine, which documents the problem without solving it.

Cleanup through the UI is only as reliable as the UI

A teardown that taps its way back works when the app is where the teardown expects. If a test fails halfway through a dialog, the teardown starts from the wrong screen, and the mess is inherited by whatever runs next. A real reset hook fixes this and nothing else does.

Eighteen minutes for four test cases

The daily routines suite took 1,089 seconds in the run we handed in. Four test cases, eighteen minutes, and almost all of it is the interface: five time pickers swiped into position, read back, then swiped into position again on the way out. Nothing here runs in parallel, and a suite this slow is one nobody sits and waits for.

Nothing runs on its own

There is no CI, no scheduled run, and no reporting beyond what Robot Framework writes locally. A suite nobody runs is documentation, and this one is closer to documentation than to a safety net.

What I Took From It

  1. Test independence is bought, not given. With an API to provision state I never had to think about who cleaned up. Without one, cleanup is a design decision in every single test, and it is the first thing to break.
  2. Naming the partition is most of the work. A constant called BLOOD_GLUCOSE_GOAL_LOW_HIGHER_THAN_HIGH tells the next reader what the case is for, which a pair of numbers in a step never does.
  3. Write down what the test needs from the world. The export quota was going to bite somebody eventually. One sentence at the top of the suite turns a future mystery failure into a known constraint.
