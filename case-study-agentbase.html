I Wrote the Spec. An AI Agent Wrote the Code.

AgentBase is a local-first desktop app where AI agents work on a task while you watch them on a live graph, and every file, shell and network call they make waits at an approval gate. I did not write its code. An AI coding agent did, from a specification I wrote first and kept in the repository from the first commit. This page is about the parts that were mine: what the specification fixed in advance, how the gate was defined and tested, and how I decided each version was ready to ship.

My role: the specification, every review, the testing and each decision to ship. That is also where responsibility sits: "the AI wrote it" explains nothing about a defect that shipped. Skill tags elsewhere on this site never point here, because the code is not my evidence; the specification and the verification record are.

  • 8 hard constraints, set before any code
  • 284 commits over six weeks
  • 15 tagged versions between 11 and 28 September
  • 1,100+ backend tests
  • 1 gate for every file, shell and network call
  • 0 listeners beyond 127.0.0.1
Scope and sources: the repository is private, so nothing here links to it, and every claim points at a file in it: the build specification, the architecture guide, the release notes, the verification record and the test suite. The personal research workflows I later ran on the app are left out; they are about how I use it, not how it was built.

Agents That Can Touch Your Machine

An agent that can read files, run shell commands and fetch pages is useful for exactly the reason it is dangerous. The specification's reason for its strictest rule says it plainly: unchecked tool calls are the failure mode behind dozens of security advisories in comparable projects. So the question was never whether to put a person in the loop, but where the loop sits and what nobody can route around.

The other requirement came from who would use it. The success criterion, written before any code, was that someone who is not a developer double-clicks an installer, types a task, and watches every spawn, tool call, handoff and completion, with no terminal, no Docker and no configuration files.

The Specification Came First

The build specification was in the first commit, on 9 September, and every session with the agent started by reading it. Its first section is a table of hard constraints, each with the reason it exists, and an instruction to stop rather than work around any of them. Five of the eight:

  • No agent frameworkThe orchestration loop is written by hand, because the live graph only works if the app owns its event stream.
  • Everything binds 127.0.0.1, hardcodedNothing reachable off the machine means nothing to expose by accident.
  • Credentials live in the OS keychainNever in an environment file, the database, a log or a command line.
  • Every file, shell and network call passes an approval gateNo exceptions, and no privileged path for any channel.
  • Chat channels act on explicit commands onlyAmbient messages never reach an agent's context, which closes the door on indirect prompt injection.

The specification also told the agent how to work, and those rules are the part I would reuse on any project. One phase per session, then stop and report what was built, what was actually run and what was not verified. Never call something working without having executed it. Write the test before the feature in the three places where silent bugs get expensive: the event store, the spending ledger and the sandbox. Report a failed approach instead of quietly substituting another. Ask before deviating from a constraint.

One Idea Everything Hangs Off

Every agent action is an append-only event. The window only projects that log, so a live run and a replay share the same code, and a window that reconnects picks up from the last sequence number it saw. The rule that follows is the one the specification states most bluntly: never send an ad-hoc message to the window; fix the event contract instead.

The Gate, and the Test That Defines It

Every tool declares a risk level. A medium or high risk call writes an approval request to the event log and blocks until someone answers it; a low risk call, reading inside the workspace, may be answered by policy. A path outside the workspace is refused before the question is even asked, and a shell command has a hard timeout that ends its whole process tree. The question itself had to be legible to a person, not raw JSON: Agent "researcher" wants to delete report.docx: Allow / Deny.

What made the gate a requirement rather than a description was its acceptance line, in the specification before the feature existed: an agent instructed to write outside the workspace root is blocked at the sandbox layer, with the denial visible in the event log. The test of that name, test_an_agent_told_to_write_outside_the_workspace_is_blocked, is in the suite.

Later I changed the default so a fresh install answers low and medium risk calls by policy and only stops for the rest. The architecture guide records the rule that change had to keep: autonomy is a policy answer, never a bypass. Every call still goes through the gate and is logged as answered automatically, with the rule that answered it; a shell command always asks; and a migration kept every existing install on the answers it already had, because a new default silently moves everyone who never chose.

Shipped When Verified, Not When Written

The repository keeps a verification record whose first line sets its terms: results cover only work actually executed. Each version shipped with release notes that say what changed and, as often, what did not. One opens: A frontend-only release. Nothing about the sidecar, the event contract, the sandbox or the budget ledger changes. That sentence is a claim a reviewer can check against the diff, which is the point of writing it.

The specification asked for the test before the feature in the event store, the ledger and the sandbox, and the backend suite grew past 1,100 tests. The pace is in the tags: fifteen versions between 11 and 28 September, five of them on 19 September alone.

What I Would Change

  • Fewer versions in one day. Five releases on 19 September outran field testing: the next release opens by fixing four issues found in the first day after the one before it. A day of real use between versions would have caught them more cheaply.
  • Settle the default before the first install. Moving from "ask for everything" to "answer low and medium by policy" was right, but doing it after people had installed it cost a migration. Defaults are decisions for every install that never changes them.
  • Name the isolation, then build it. The specification says honestly that the shared build does not isolate shell commands at the operating-system level, and offers containers only as an option for my own instance. The honesty is right; the gap is still a gap.

Key Engineering Learnings

  1. A specification is a test plan someone else can run. Constraints with reasons and acceptance lines told the agent what done meant, and told me what to check.
  2. Owning the event stream is what makes a system observable. Refusing a framework cost a hand-written loop and bought a live graph and a replay from one log.
  3. Autonomy should be a policy answer, never a bypass. An automatic yes still passes the gate and leaves a record.
  4. Claim only what was executed. The working rule I gave the agent is the one I hold myself to on this page.
