Two Writes for One Short Link

A URL shortener is the smallest service that still has to answer a real design question: where does the short code come from? Hash the URL and you have invited collisions, plus all the machinery for resolving them. This one takes the id MySQL issues for the row and encodes it in Base62, which makes a collision structurally impossible and creating a link a two-statement operation, because a code derived from the row cannot be computed until the row exists.

My role: self-directed, with no team and no brief. That cuts both ways: nothing here was handed to me and nothing here was reviewed by anyone else either. The service is small enough that every decision in it had to be argued rather than absorbed from a framework default, which is what the page is about. The section worth reading is the one where a Spring convenience silently overrode a column default the schema had already declared.

  • 2 endpoints, one to create, one to follow
  • 6 classes across four layers
  • 1 table, 4 columns, 1 index
  • 2 statements to create one link
  • 4 tests, 3 unit and 1 integration
  • 62 characters in the code alphabet
Scope, and where the numbers come from: the service is deliberately small. Two endpoints and one table, with everything a production shortener needs next, a cache in front of the redirect, click analytics off the request path, rate limiting, more than one host, argued about at the end rather than built. Every status code quoted here was taken from the running service against a local MySQL rather than from the README, and the one place those two disagreed is written up below as the defect it is.

The Whole Contract, in Two Endpoints

One endpoint creates a code for a URL and one follows a code back to it. There is no account, no dashboard and no delete, and the surface stays this small on purpose: every feature past these two would have bought less than the time it cost to defend the two. 

$ curl -s -X POST localhost:8080/api/v1/urls \
    -H 'Content-Type: application/json' \
    -d '{"url": "https://spring.io/projects/spring-boot"}'
{"code":"5"}

$ curl -sI localhost:8080/5
HTTP/1.1 302
Location: https://spring.io/projects/spring-boot

A code that does not exist gets a 404. Nothing else is defined, which is the point of writing the contract down before the schema.

Behind those two calls are four layers, and the reason to keep them apart is that each one is then allowed to know exactly one thing. The controller knows HTTP, the service knows the rules, the repository knows SQL, and the id that the whole design turns on is known only to the database until it says so.

The Code Comes From the Row It Names

The obvious generator is a hash of the URL, truncated to something short. It is one statement, it is stateless, and it is wrong for a reason that only shows up later: truncate a hash far enough to be typeable and two different URLs will eventually produce the same code. That is not a bug you can decline to have. It is a branch you have to write, test, and pay for on every insert, forever.

The alternative is to encode something already unique. MySQL issues a unique AUTO_INCREMENT id for every row, so the code can be that number written in base 62, using the digits, the lowercase letters and the uppercase letters. Base62 of a unique number is unique because the encoding is a bijection, not because anyone checked. There is no collision path to write, because there are no collisions to resolve.

The cost arrives immediately. If the code is a function of the id, and the id is issued by the insert, then the code cannot be part of that insert. Creating one short link is therefore two statements and not one.

Where the short code comes from: the options weighed
OptionWhat it buysWhat it costs
Hash the URL, truncatedOne statement, and no state to keepTwo URLs eventually share a code, so every insert carries a collision branch, forever
Base62 of the row's own idNo collision is possible: the encoding is a bijection, not a checkThe id comes from the insert, so creating a link takes two statements

The encoding itself is a loop of two jobs that are easy to blur together. The remainder picks a character, and the division shrinks the number for the next round. It builds the string from the least significant digit up, which is why each character is inserted at the front rather than appended. 

// 0 -> "0", 61 -> "Z", 62 -> "10", 63 -> "11"
StringBuilder code = new StringBuilder();
while (counter > 0) {
    code.insert(0, ALPHABET.charAt((int) (counter % BASE)));
    counter /= BASE;
}

Sixty-two characters give four billion codes in six of them, which is more room than this service will ever need and a great deal shorter than a UUID.

One Table, and What Each Column Had to Earn

CREATE TABLE urls (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    short_code  VARCHAR(10)   UNIQUE,
    long_url    VARCHAR(2048) NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

The primary key is id and not short_code, even though the code is what the outside world uses. A key should be a meaningless, stable handle rather than business data that a later decision could change: swap the generator and every short code changes, and any table that had pointed at one would be pointing at nothing. Practically, it is also the number the encoder needs, so the surrogate key pays for itself twice.

short_code is UNIQUE, which in MySQL also builds the index that the redirect lookup uses, so one keyword buys the guarantee and the query plan together. What it is not is NOT NULL, and that omission is the diagram above showing up in the schema: at the moment of the insert the code genuinely does not exist yet. MySQL permits several nulls under a unique constraint, so nothing is weakened for the rows that do have a code.

Worth being precise about what that constraint is for. It is not the uniqueness mechanism, because Base62 over an auto-increment id cannot produce a duplicate. It is a safety net against a future application bug: if someone later replaces the generator with something that can repeat, the database refuses the write instead of quietly serving two destinations from one link.

long_url has no index at all, which is the decision most likely to be challenged and the easiest to defend: nothing in the service ever queries WHERE long_url = ?. An index is not a free win. It costs write speed and disk on every insert, and it earns that back only where a lookup actually uses it. Duplicates are fine here too. Two people shortening the same URL get two codes, and collapsing them would only matter to a feature this service does not have.

An Explicit NULL Is Not a Missing Column

created_at was declared DEFAULT CURRENT_TIMESTAMP and came back null on every row. The schema was right, the insert named no such column, and the data was still wrong, which is the combination that makes a bug hard to see: there is nothing to read that looks incorrect.

The cause was a convenience. Spring's SimpleJdbcInsert, given a table and nothing else, inspects every column that table has and writes an explicit NULL for each one it was not handed a value for. SQL applies a column default when the statement omits the column, not when the statement names it and sets it to null. The default was never skipped, exactly: it was overruled by a value the application did not know it was sending.

Finding it meant giving up on reading the application and reading the database instead. MySQL's general_log records the literal SQL a connection sends, which turned an argument about what the code probably did into a line of text about what it actually sent. The fix was one call, pinning the insert to the single column it has a value for: 

this.insertUrl = new SimpleJdbcInsert(jdbcTemplate)
        .withTableName("urls")
        .usingColumns("long_url")          // the whole fix
        .usingGeneratedKeyColumns("id");

Rows written after this carry the timestamp the schema always said they would.

The general lesson is worth more than the fix. A default is a property of the statement, not of the table, and any layer that generates SQL on your behalf is deciding the shape of that statement for you. That is fine while what it generates is what you would have written. It stops being fine the moment it is more thorough than you were.

302, Because 301 Is a Decision You Only Make Once

A redirect wants a status code, and 301 is the one that sounds right: the destination really is permanent. It is also the one the browser is entitled to cache, which means the second click on a short link never reaches this service at all. Every count, every referrer, every piece of evidence that the link is being used, gone, and gone silently, because a cached redirect looks exactly like a working one.

302 gives that up and buys a round trip. Every click comes back to the server, which costs a little latency per click and keeps the option of ever knowing anything about those clicks. It is worth being honest about the size of that trade here: nothing in this service counts a click today. The status code is not paying for a feature, it is declining to foreclose one, and if analytics were ruled out for good then 301 would be the better answer.

What the Tests Prove, and What They Only Appear To

Three unit tests run against a mocked repository, so no database is involved: creating a code and resolving it back, rejecting a blank URL, and returning null for a code that does not exist. The mock replaces the database boundary and nothing else, which is the detail that makes the first test worth running. The Base62 encoder is not stubbed, so asserting that id 62 produces the code "10" exercises the real logic and not a canned answer.

The blank-URL test is the one I would defend hardest, because of its second assertion. 

assertThrows(IllegalArgumentException.class, () -> service.createShortUrl("   "));

// assertThrows only proves an exception happened somewhere.
// This proves it happened before the guard's whole job, keeping
// junk out of the table, could have been bypassed.
verifyNoInteractions(repository);

Delete the second line and the test still passes against a service that inserts the row first and fails afterwards.

The fourth test is a different animal wearing the same annotation. The generated contextLoads boots the entire Spring context, which means it opens a real connection and fails when the MySQL container is not running. It is an integration test, and the useful thing is not the count of four but being able to say which of the four needs a database and why.

What It Does Not Do

A blank or missing URL is rejected in the service, before anything reaches the database, and the guard works: the table is unchanged after a rejected request. What is missing is the last step. Nothing translates the IllegalArgumentException into a status code, so the caller gets a 500 where the honest answer is 400. A @ControllerAdvice handler is the fix and it is not written.

The README claimed the 400 until this page was written. Checking it against the running service is what turned a documented contract back into a defect, and it is the reason every status code quoted here came from a request rather than from prose.

Nothing checks that the string is a URL at all. "definitely not a url" is accepted, stored, and answered with a 200 and a working code. The failure is deferred to whoever follows the link, who gets a 500 from a service that was perfectly happy when the value went in. Validation at the boundary is the fix, and the interesting part is where the error surfaces: the person who made the bad request is not the person who pays for it.

The codes are also, by construction, guessable. Encoding a counter means /1, /2 and /3 walk the table in order, so a short link here is not a private one. That is the price of making collisions impossible rather than merely unlikely, and it is a fair trade only while nothing behind these links is meant to be unlisted.

Beyond that: no cache in front of the redirect, so every click is a database read; no click analytics, which the 302 exists to keep possible; no rate limiting; one host; and the development password sits in application.properties, which is fine for a throwaway local container and wrong anywhere a real secret belongs.

Key Engineering Learnings

  1. Prefer the design with no failure mode over the one with a good handler. A truncated hash needs collision detection, a retry path, and a test for both. Encoding a number that is already unique needs none of them, and the cost is paid somewhere far more visible: the write splits in two.
  2. A default is a property of the statement, not of the table. A column default fills a column the statement leaves out. Name that column and set it to null and the default is overruled, which is exactly what a helpful driver did on my behalf until I read the SQL it was really sending.
  3. When the code and the data disagree, read the wire. The application said it inserted one column and the rows said otherwise. MySQL's own log settled it in a minute, and no amount of rereading the Java would have.
  4. A guard clause is only worth what it stops. Asserting that an exception was thrown says nothing about when. Asserting that the repository was never touched is what pins the check to the side of the boundary where it protects something.
  5. Test the README. It documented a 400 that the service has never once returned. Documentation drifts in exactly the places nobody re-runs, and the endpoint contract is the worst possible place to let it.
