Where the Database Can Say No

A campus makerspace lends out 3D printers, laser cutters and CNC mills on a paper sign-up sheet. The sheet cannot stop two people claiming the same slot, cannot tell whether either of them has been trained on the machine, and keeps no record when something comes back late or broken. I replaced it with a three-tier web application over a PostgreSQL schema, and the project turned into one question: of the rules that matter, which ones can the database refuse by itself, and what do you do about the ones it cannot reach?

My role: self-directed, with no team and no brief, which cuts both ways: nothing here was handed to me and nothing here was reviewed by anyone else either. The method is textbook. The parts worth reading are the ones I did not plan, three defects that surfaced only because the analysis ran against real rows instead of the schema.

  • 14 relations, 5 views, 21 foreign keys
  • 28 constraints declared in the schema
  • 4 migrations, applied in order from empty
  • 13 relations analyzed for dependencies
  • 19 screens covering 19 user stories
  • 687 bookings seeded across 85 members
Scope and credit: the makerspace is invented and so is every person in it. The three rooms borrow the name of a real building at Taipei Tech for a recognizable setting, and nothing else about that building, its equipment, or any actual campus operation is represented here. The seeded members, fines and certifications are fabricated to exercise specific query branches, which is the point of them.

Three Rules a Sign-Up Sheet Cannot Keep

The paper sheet has three failure modes, and each one is a rule waiting to be written down. Two members write their names in the same slot and both turn up. Nobody records whether the person signing up has been trained on that machine, so staff check by memory or do not check. A machine comes back two days late and nothing happens, because nothing was written down that a charge could be based on.

So the system exists to enforce exactly three things: one booking per machine per time slot, no booking without a current certification, and a recorded, chargeable consequence for an overrun or damage. Everything else in the schema is there to serve one of those.

The interesting part is that the three are not alike. The first is a range-exclusion constraint the database can enforce on its own. The second spans five tables and depends on the booking window, which no CHECK may look at. The third is arithmetic that a person has to approve before it becomes money owed. One rule the schema refuses outright, one it cannot reach, one it should not decide.

Choosing the Database for One Constraint

"No two bookings for the same machine may overlap" is the rule most systems implement in application code: read the existing bookings, decide, insert. That has a race window between the read and the insert, and under two people clicking Confirm at the same moment it is the window that loses you the machine. PostgreSQL can state the rule as a table constraint instead, which is the reason it was picked over anything else.

How the no-overlap rule could be enforced
OptionWhat it buysWhat it costs
Check in application code: read, decide, insertWorks on any databaseA race window between the read and the insert: two people confirming at once can both win
A PostgreSQL exclusion constraintTwo concurrent inserts for one slot cannot both succeed, and its GiST index also serves the availability search, at about 2 msThree details to get right: tstzrange, a WHERE clause that frees canceled slots, and half-open ranges
 
-- 001_create_schema.sql: the one load-bearing rule the database keeps by itself
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE booking ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (
    equipment_id                  WITH =,
    tstzrange(starts_at, ends_at) WITH &&
  ) WHERE (status <> 'cancelled');

Two concurrent inserts for the same slot cannot both succeed, whatever the application code does or forgets to do.

Three details in those six lines are each a question a demo attracts. It is tstzrange and not tsrange, because the latter takes a timestamp without a time zone and would drag the columns to the wrong type. The WHERE clause is what lets a canceled booking release its slot: without it the slot would stay blocked forever, and the member who dropped it could not book it again. And tstzrange is half-open by default, so a booking ending at 14:00 and one starting at 14:00 do not collide, which is the definition the rest of the system uses anyway.

The constraint also pays for itself twice. Enforcing it builds a GiST index on (equipment_id, tstzrange(starts_at, ends_at)), and that is exactly the index the availability search wants. The integrity guarantee and the query plan are the same object. Measured against a fresh seeding rather than assumed, that search settles at about 2 ms steady state, roughly 250x inside the specification's 500 ms budget, and EXPLAIN confirms the per-machine conflict check is served by an Index Scan on the same constraint.

The Rule With No Declarative Home

The load-bearing rule of the whole project is the second one: a member may book a machine only while holding a certification that authorizes that machine's category. It spans five tables and depends on the booking window, so it has no home in a CHECK, and it is too important to leave scattered across whichever code path happens to run.

It also has an interpretation to settle before any of that. Valid when? I took the strict reading: valid across the entire window, not merely on the day the booking is made. A member whose certification expires on Friday may not book Saturday, and may not book a window that starts Thursday and ends Saturday. The looser reading would let someone reserve a machine they will not be qualified to operate when they walk up to it, which defeats the rule it is supposed to be.

The database's contribution is a view rather than a trigger. It flattens the traversal into one relation of member, category and validity window: 

-- the whole traversal, flattened into (member, category, window)
CREATE VIEW v_member_category_authorization AS
SELECT g.member_id, ca.category_id, g.certification_id,
       g.granted_at AS valid_from, g.expires_at AS valid_to
FROM certification_grant AS g
JOIN category_authorization AS ca ON ca.certification_id = g.certification_id;

The booking transaction then satisfies the rule with one query: a row must exist whose category matches the machine's and whose window covers the whole booking, that is valid_from <= starts_at AND valid_to >= ends_at.

A trigger would have enforced it more forcefully and documented it worse. The view states the rule in the schema in a form you can read, the booking transaction is the single place that applies it, and the catalog reuses the same view for the "am I certified for this?" column, so the answer a member sees and the answer the server enforces come out of one definition.

Two consequences fall out of the same reading. Certification is re-checked at handover, because a booking made legitimately in March can belong to a member whose training lapsed in April: the desk refuses the handover, and the booking is not deleted. And expiry is never retroactive, so a completed booking stays valid history after the certification behind it expires. History is not rewritten by the passage of time.

Fourteen Rules, and Where Each One Lives

The schema declares 28 CHECK and EXCLUDE constraints and 21 foreign keys, every one with an explicit ON DELETE action. The rule I held myself to is that anything expressible declaratively is declared, because a database constraint cannot be bypassed by a code path that forgot to check. What follows is the split, and the reason each rule sits where it does.

Business rules, what each says, and where it is enforced
Rule What it says Enforced by
No overlap Two non-canceled bookings for one machine may not overlap in time Database EXCLUDE USING gist
One handover A booking has at most one checkout, and a checkout at most one return Database UNIQUE (booking_id)
No self-grant Nobody may grant a certification to themselves Database CHECK granted_by <> member
Retire, never delete A machine with booking or maintenance history is retired by status change Database ON DELETE RESTRICT
Documented waiver A waived fine records a reason and the staff member who waived it Database CHECK penalty_waiver
Certification No booking without a certification valid across the whole window Application spans five tables
Downtime No booking in a window that intersects scheduled maintenance Application range join, another table
Unpaid fines Outstanding fines at or above the threshold block new bookings Application aggregate over penalty

Eight of the fourteen. The top five are unbypassable and the bottom three are only as good as the transaction around them, which is why each of those lives in exactly one file.

The bottom three are not application rules because I preferred them there. Each names its own reason: one queries other tables, one compares ranges across a table boundary, one needs an aggregate. A CHECK can do none of those. Writing the reason next to the rule turned out to matter more than the split itself, because it is the difference between a documented limit and a habit.

One rule is deliberately not automated at all. When a return comes in late the system computes the overrun and proposes a fine from the hourly rate, and then stops: staff confirm, adjust or decline it. The arithmetic is the machine's job and the charge is a person's.

Normalization That Read the Data, Not the Schema

Thirteen relations went through a functional-dependency analysis: candidate keys, dependencies, then 2NF and 3NF with the ruled-out cases shown rather than asserted. Eleven were already in BCNF. That is a claim about the earlier design rather than luck: surrogate keys everywhere, natural keys kept as UNIQUE, and multivalued attributes resolved into entities before translation leave few places for a transitive dependency to hide.

The two that needed work needed different work. In equipment, a machine's product model determines what class of machine it is, so (manufacturer, model) determines category_id while being nothing like a key: twenty machines carried only fifteen distinct model-and-category combinations, and the four Prusa MK4S printers each stored their own copy of the fact that an MK4S is an FDM printer. The anomaly that permits is a one-row update that re-files one printer under "laser cutter" with nothing to object, after which the certification rule would demand a laser certification for that machine and an FDM one for the three identical machines beside it. That decomposes into an equipment_model relation, with the migration re-checking the lossless join inside its own transaction and rolling back if it fails.

The one that decomposed into a table that already existed

The second is more interesting. A fine raised from a booking is assessed against the member who made that booking, so booking_id determines member_id in penalty. Textbook 3NF says extract the dependency into its own relation. Do that and you get (booking_id, member_id), which is a projection of booking: the determinant and the dependent already live together in a table where the determinant is the primary key. Materializing it would create a second copy of something the schema holds already. 

-- 004_normalize.sql: enforce the dependency against the table that already holds it
ALTER TABLE booking ADD CONSTRAINT booking_id_member_unique UNIQUE (id, member_id);

ALTER TABLE penalty DROP CONSTRAINT penalty_booking_id_fkey;
ALTER TABLE penalty ADD CONSTRAINT penalty_booking_member_fk
  FOREIGN KEY (booking_id, member_id) REFERENCES booking (id, member_id)
  ON DELETE RESTRICT;

The unique constraint is redundant as a uniqueness claim, since id is already the primary key. PostgreSQL requires it before it will accept the composite foreign key, and that one index is the entire cost of the fix.

Manually assessed fines have no booking, and they stay legal without special handling: the default matching semantics skip the check when any referencing column is null. The constraint applies to exactly the rows the dependency holds on.

What that is worth stating honestly is that penalty was not decomposed and strictly remains in 2NF. Its attributes are unchanged. What changed is that the anomaly 3NF exists to prevent has become unstorable, which was the actual goal. Before this, four separate places in the repository compensated for the dependency in prose and procedure: the ER model, the decision log, a column comment, and a self-check in the seed script. None of them stopped a bad write.

Three Defects Only the Rows Could Show

The obvious way to write a dependency analysis is to read the schema. I derived them from the seeded instance instead and checked each one with a query, which is slower and caught three defects that the schema could not have shown. All three are the same class: data that looked populated but was degenerate, so independent columns were indistinguishable from dependent ones.

  1. A generator that made two columns constant per member. Heavy users were picked with k % 20 and their checkouts decided by k % 10. Because 10 divides 20, both predicates were constant within a member: each heavy user had a checkout on every booking or on none, and returned everything late or nothing late. The totals still looked healthy. It was visible only in the activity view, where every top member showed zero no-shows and zero late returns, which is worse than an empty column because it survives a glance.
  2. Timestamps that were equal in every single row. Every maintenance event had its report time exactly equal to its downtime start, and every closed event its completion exactly equal to its downtime end. Derive dependencies from that data and you conclude the table violates 3NF through two mutual dependencies that do not exist. The fix was to make the seed tell three truer stories: a fault found during scheduled servicing starts downtime before the report, one left in service until triage starts after, and paperwork can close after the machine is already back.
  3. A twenty-way tie produced by the Chinese remainder theorem. The "members above the site average" report returned rows that were byte-identical for most of its length, all showing the same booking count. Heavy users were assigned k % 20 under the selection predicate k % 43 < 20, and since 43 and 20 are coprime, those pairs are uniform: every heavy user received exactly the same number of bookings. A screenshot of that reads as fabricated data, and the query's real question, who are the heavy users, is not answered by a list that cannot rank them. Drawing the index from a weighted array instead fixed the distribution; the report now returns six rows with six distinct counts and no ties at all.

The third one is the one I would not have found any other way. The arithmetic was plausible, the row counts were right, the shape of the distribution was the shape the seed comments argued for, and the defect was that the heavy mode had zero internal variance. The schema cannot tell you that your data is accidentally consistent.

It also changed how I read the seed script. Seed data written to fill tables produces reports that look full; seed data written backwards from the queries produces reports with both branches of every conditional exercised, and it is the second kind that makes a degeneracy findable at all.

The Redundancies I Kept, and the Constraint I Left Out

Four redundancies survive in the schema, and presenting it as redundancy-free would have been false. Three of them are across tables, which 3NF has nothing to say about, since it is defined over the attributes of one relation.

Two of those three are snapshots that exist precisely so history cannot be rewritten. A certification grant stores its own expiry rather than deriving it from the certification's validity period, because deriving it would let an edit to that period retroactively expire grants issued years ago. A checkout stores its own due-back time rather than reading the booking's, because the due time is fixed at the moment of handover and a derived one would silently re-date a loan already in progress. Enforcing either dependency would leave the schema in the same normal form and make it strictly worse, which is a harder thing to argue than a clean decomposition.

The constraint I did not add is the one that looks most obviously right. Renewing a certification creates a new grant that supersedes the old one, and the natural way to enforce "supersedes" is an exclusion constraint forbidding two overlapping validity windows for the same member and certification. It would also make it impossible to renew before expiry, which is the normal case and exactly what the thirty-day warning on the dashboard exists to encourage. Its absence is a decision, not an oversight, and it is written down as one.

What It Does Not Do

Sessions are bearer tokens held in a map inside the API process. They do not survive a restart, and they would be wrong for anything but a single-node project like this one. A signed token or a shared session store is the fix, and it is not written.

The containerized database path is written and unverified: Docker was not installed on the machine this was built on, so the compose file and its init scripts have never once been executed. The local PostgreSQL path is the one that actually runs. That is in the README in those words, because a setup step nobody has run is not a setup step.

And extending a booking, the one feature that breaks the system's own convention, ships as an in-place update to the end time. Every other state change here is append-only. This one destroys the original window and keeps no record of what it was, which is the version I would replace first, with an extension entity rather than a quieter UPDATE.

Key Engineering Learnings

  1. Pick the tool for the constraint you cannot afford to lose. One rule decided the database, and the constraint that enforces it also builds the index the main query needs. Turning a race condition into a schema-level impossibility is worth choosing a stack over.
  2. A rule that cannot be declared should still live in exactly one place. Three rules here span more tables than a constraint can reach. What kept them honest was not cleverness but location: one transaction, one file, and a written reason for why the database is not holding them.
  3. Documenting a dependency is not enforcing it. Four places in the repository described the same redundancy correctly. A single wrong UPDATE would have gone through all four. The composite foreign key that replaced them is one line and cannot be argued with.
  4. Derive dependencies from the data, not from the schema. Reading the DDL alone would have reported two relations as violating 3NF when they do not, and sent a twenty-row tie into a report as a finding. Data can be accidentally consistent, and a schema has no way to tell you so.
  5. Say which parts you did not run. An unexecuted Docker path, a session store that will not survive a restart, and a feature that breaks the model's own convention are all more useful written down than quietly implied to work. It costs a paragraph and it is the difference between a limitation and a surprise.
