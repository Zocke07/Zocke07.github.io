Between the Code and the People

Six interns, spread across two countries, building two internal AI products for a large telecom. A new team with no QA engineer assigned, no automated suite on the product that needed one most, and a codebase where a meaningful share of the code was written with AI assistance and therefore looked plausible whether or not it worked. Somebody had to decide when each change was actually ready. That was my job.

My role: part technical program manager for the remote team, part the person who tested the thing before anyone else had to trust it. I coordinated the work and owned the verification gate. The products themselves are the team's build.

  • 6-person distributed team
  • 2 internal AI products built
  • ~40 specified changes in about two months
  • 300+ written acceptance criteria across those changes
  • Spec-driven delivery, proposal before code
  • Hands-on sign-off before release

A note on confidentiality: this write-up respects my obligations to my employer. Internal service names, hostnames, endpoints, rule documents, and business logic are omitted or generalized. What remains is engineering practice that would look familiar at any company. Scale figures describe team output, and my personal contributions are called out explicitly.

The Problem

An intern team is a strange engineering unit. Everyone is capable, nobody has context, and the people who could answer questions are busy doing their own jobs. Ours was also split across two locations, which meant the cheapest way to resolve a misunderstanding, turning around and asking, was unavailable.

Both products leaned heavily on large language models, and much of the code was written with AI assistance. That combination creates a specific failure mode. AI-written code compiles, reads cleanly, passes review, and is confidently wrong in ways that only show up against a real system. Type checking cannot catch a translation that silently drops hyperlinks. Code review cannot catch a preview pane that shows one result while a different one gets written to the live record.

So the actual problem was not writing features. It was building enough process that six people could move in the same direction, and enough verification that we could tell the difference between code that looked finished and code that was.

What We Built

Two products, both wrapping a language model in a workflow people would actually use inside tools they already had open.

  • AI Code Review Assistant

    Internal IDE Extension

    An AI code-review assistant for the editor. It reads the code you are working on, reduces it to the regions worth examining, checks it against the organization's own written development standards, and reports findings inline on the offending lines.

    Under the hood: a TypeScript extension host and a React sidebar joined by a fully typed message bridge, a provider abstraction so the model vendor is swappable, syntax-tree parsing to trim what gets sent, schema-validated JSON for the scan results, and a sanitization layer on everything the tool sends.

  • Localization Assistant

    Browser Extension

    A translation workflow embedded beside an internal content-authoring portal. It reads the source content out of the page, streams a translation into a preview, and writes the approved version back through the page's own editor.

    The hard part was the boundary. A Manifest V3 extension that changes nothing in the host application has to preserve images and inline markup through a translation round trip, and keep what the reviewer approved identical to what gets written.

The Verification Gate

With no automated suite on the localization tool, "done" needed a definition that did not depend on how confident the author felt. We adopted a spec-driven workflow, and I enforced it as the release gate. Every change moved through the same sequence, and it did not ship until the last step passed.

  1. Written proposal and designWhat problem, what approach, what trade-off. Agreed before code, so remote reviewers were not reverse-engineering intent from a diff.
  2. Acceptance criteria in explicit WHEN/THEN formIncluding the negative paths: timeouts, degenerate inputs, provider failures, and explicit regression floors.
  3. Implementation against a numbered task checklistEach item individually checkable, so partial progress was visible across time zones without a status meeting.
  4. End-to-end verification, by handThe step I owned. A real browser against a real running instance, naming the exact target, the expected signal, and the pass criterion.
  5. Explicit sign-off, or a recorded decision not toWhen we accepted a gap or skipped a pass, that call was written down with its reason rather than left implied.

The fourth step is where the process earned its cost. Fixes that were believed complete repeatedly turned out not to be: a write-back path that worked in isolation flattened hyperlinks to plain text against the real editor, and a long translation was silently truncated by the model before it ever reached the page. Neither was visible in the diff. Both were obvious within a minute of using the thing.

On the IDE extension, verification looked different because a test suite was possible there. The team's answer covered three genuinely awkward dependencies, a live editor API, a real version control system, and a non-deterministic model, by running tests inside a real editor instance, building throwaway repositories on disk to exercise real commands, and stubbing the model so results were deterministic and cost nothing to run. Reviewing that suite is where I learned most of what I now know about testing the untestable.

Keeping Six People Aligned

The program management half of the job was mostly about removing ambiguity before it became rework. Sprint tasks tracked in Jira gave the on-site engineers and the remote team one shared view of state. The written proposal-and-design step meant disagreements surfaced while they were still cheap, in a document, rather than after someone had built the wrong thing for a week.

The part I underestimated was how much of the role is translation, in the human sense. On-site engineers had context the remote team could not see, and the remote team hit problems that never reached the people who could unblock them. A lot of the value I added was noticing that two people were confidently talking about different things.

Key Engineering Learnings

  1. AI-assisted code needs a different kind of review. It fails confidently rather than obviously. The reviewer's job shifts from "is this written well" to "does this actually do what it claims against a real system", and only running it answers that.
  2. Writing the acceptance criteria first is the cheapest quality tool there is. Writing explicit WHEN/THEN criteria forces the negative paths into the open at design time, when they cost a sentence instead of a release.
  3. A gate is only real if it can say no. Recording the times we accepted a gap made the sign-offs mean something, because approval that is never withheld carries no information.
  4. Distributed teams pay for ambiguity in days, not minutes. Written intent up front is not bureaucracy when the person who would have answered your question is asleep.
  5. Being the last person before release changes how you read code. You stop asking whether it is correct and start asking how you would know, which turns out to be the more useful question.
